> **评测协议说明（当前版本）**：本页 v2/v3 数字是历史实验记录，其中开集
> `best F1` 和 `R@100%P` 来自同一 split 上的 oracle threshold sweep，只能描述
> 分数可分性，不能当作部署阈值的泛化结果。当前代码要求用

# v3：经典 → 现代

## 0. 这一轮在做什么

不是"用更好的方法"，而是：

> **先用经典方法搭出完整 pipeline 并量化每一级的能力边界，然后逐级替换成现代方法，再量化每一级的贡献。**

每一次替换都挂着一个 v2 实测出来的动机数字：

| 环节 | 经典 | → 现代 | 替换动机（v2 实测） |
|---|---|---|---|
| 检索特征 | ResNet18 + GAP | **DINOv2** | 跨域泛化差（泛化间隙 34.8 点） |
| 训练目标 | triplet loss | **InfoNCE** | 24% 零梯度、需手写挖掘 |
| 几何验证 | ORB + RANSAC | **DISK + LightGlue** | 昼夜判别力 1.1×，等同随机 |
| 评测设定 | 闭集 | **开集 + 拒绝** | 门控机制无法被衡量 |

## 1. 闭集主表

**held-out `night_right` 070-099（30 query，训练时从未见过）**

| # | 配置 | R@1 | R@5 | R@10 | P@5 | R@100%P |
|---|---|---:|---:|---:|---:|---:|
| ① | ResNet18-GAP 预训练 | 0.500 | 0.767 | 0.900 | 0.433 | 0.000 |
| ② | ResNet18-**GeM** 预训练（零训练） | 0.533 | 0.800 | 0.867 | 0.407 | 0.000 |
| ③ | ResNet18-GAP + **triplet** | 0.633 | 0.933 | 1.000 | 0.527 | 0.000 |
| ④ | ResNet18-GAP + **InfoNCE** | 0.633 | 0.900 | 0.967 | 0.593 | 0.000 |
| ⑤ | **DINOv2 CLS**（零训练） | **0.933** | 0.967 | 1.000 | 0.753 | 0.167 |
| ⑥ | **DINOv2 patch-mean**（零训练） | **0.933** | 0.967 | 1.000 | **0.800** | **0.900** |
| ⑦ | ⑥ + 因果序列匹配 | **1.000** | 1.000 | 1.000 | 0.933 | **1.000** |
| ⑧ | ⑥ + 非因果序列匹配 | **1.000** | 1.000 | 1.000 | **0.960** | **1.000** |

### 1.1 头号结论：零训练 > 微调 ⭐

```
ResNet18 预训练             R@1 0.500
ResNet18 在 60 帧上微调      R@1 0.633
DINOv2 零训练               R@1 0.933      ← 高出微调版 30 个点
```

**在只有 60 个训练样本的场景下，"换一个泛化能力本来就强的特征"完胜"在小数据上微调"。**

这直接印证了 v2 的诊断：微调的泛化间隙是 34.8 点，说明它学到的大部分东西不可迁移；而 DINOv2 的跨域能力来自海量自监督预训练，不需要在目标域上训练。

**且优势是域特异的**：在 `day_right`（仅视角变化）上所有配置都在 0.94~0.98，**DINOv2 的增益精确集中在跨域场景**。

### 1.2 ⑤ vs ⑥：R@1 相同，但置信度质量差 5 倍 ⭐

这是本表最容易被略过、但信息量最大的一对：

```
⑤ DINOv2 CLS        R@1 0.933   R@100%P 0.167
⑥ DINOv2 patch-mean R@1 0.933   R@100%P 0.900
```

**检索准确率完全相同，零假阳性下的召回却差 5.4 倍。**

含义：patch-mean 不只是"一样准"，它的**相似度分数本身校准得好得多**——排在最前面的那些预测几乎全对，所以可以放心地设一个高阈值。CLS 的分数则没有这个性质。

> 📌 **这条说明了为什么不能只看 R@1。** 对 SLAM 而言，"高置信度的预测是否可信"比"平均准确率"更关键。
>
> 也补充了 AnyLoc"patch 聚合优于 CLS"这个结论的一个新侧面：**优势不只在精度，更在置信度可靠性**。

### 1.3 GeM 与 InfoNCE：机制成立，但增益进了噪声

**GeM（②）**：R@1 0.500 → 0.533，只有 1 个 query 的差别。但在**全部 100 个 night query** 上（零训练模型无污染，样本量 3.3 倍）差别更清楚：

```
GAP 224   R@1 0.510        GAP 384   R@1 0.450
GeM 224   R@1 0.570 (+6.0) GeM 384   R@1 0.530 (+8.0)
```

**高分辨率反而有害**，而且机制解释得通：`384/32 = 12`，layer4 从 `7×7=49` 变成 `12×12=144` 个位置，**GAP 要平均的位置多了 3 倍，稀释更严重**。如果稀释是主因，GeM 在 384 上应该帮得更多——实测正是如此（+8.0 vs +6.0），**两个观察互相印证**。

**InfoNCE（④）**：held-out R@1 与 triplet 完全相同（0.633），只有 P@5 略高（0.593 vs 0.527）。详细诊断见 §2。

### 1.4 序列匹配仍是单项最大增益

`0.933 → 1.000`，且 `R@100%P` 从 0.900 到 1.000。**因果版（只用过去帧，在线 SLAM 的真实条件）与非因果版打平**，说明这里不需要未来信息。

⚠️ 但 v2 已记录的前提仍然成立：Gardens Point 逐帧对齐、速度稳定，**对序列假设过于友好**。多速度搜索的实测显示，把速度范围放宽到 0.5~1.5 会让 night R@1 从 0.890 掉到 0.780——**多速度搜索不是免费的，它同时扩大了误匹配得高分的机会**。

## 2. InfoNCE 的诊断：机制可测，收益不可测

初始配置下 InfoNCE **输给了** triplet（val R@1 0.70 vs 0.80）。诊断指标直接指出原因：

```
triplet:  零梯度三元组  10% → 67% → 78% → 92% → 97% → 98%
InfoNCE:  batch=16 只有 6.6 个有效负样本；
          梯度权重 >1% 的负样本 6.6 → 0.9，in-batch top1 第 3 个 epoch 就到 1.00
```

**两者都会饱和，只是方式不同**：triplet 是"满足 margin 后归零"，InfoNCE 是"in-batch 任务变得太简单"。

按诊断调整后：

| batch | tau | 有效负样本 | 梯度>1% 的衰减 | val R@1 |
|---:|---:|---:|---|---:|
| 16 | 0.07 | 6.6 | 6.6 → **0.9** | 0.70 |
| 32 | 0.07 | 13.4 | 13.4 → 3.7 | 0.70 |
| 60 | 0.07 | 27.1 | 26.9 → 18.3 | **0.90** |
| **60** | **0.2** | 27.1 | **27.1 → 27.1（完全不衰减）** | **0.90** |

三点结论：

1. **负样本数直接决定成败**（6.6 → 0.70，27 → 0.90）——B3 预言的"batch 太小"完全应验，而且 `negative_gap=20` 的 mask 把 15 个候选砍到只剩 6.6 个
2. **tau=0.2 时梯度权重完全不衰减**，这是"温度是难样本聚焦旋钮"的直接实证
3. 调好后 val R@1 反超 triplet（0.90 vs 0.80）

**但 held-out 上两者都是 0.633。** 验证集只有 10 个 query，0.80 与 0.90 相差就是 1 个 query——**那个优势是噪声**。

> **诚实结论：InfoNCE 的机制优势是可测量的（梯度诊断），但在这个数据规模下没有转化为可测量的检索性能提升。**

## 3. 几何验证：判别力对照 ⭐

32 个采样点，**两个方法使用完全相同的配对**（早期版本让两方法从共享随机数生成器里各取各的负样本，不公平，已修正）：

| 方法 | Query 域 | 正确配对内点 | 错误配对内点 | 均值比 | 逐样本可分 |
|---|---|---:|---:|---:|---:|
| ORB | day_right | 126.5（中位 96） | 26.9（中位 26） | 4.7× | 97% |
| **ORB** | **night_right** | **27.0**（中位 26） | **25.7**（中位 26） | **1.1×** | **56%** |
| DISK+LightGlue | day_right | 446.4（中位 466） | 9.6（中位 10） | **46.7×** | 100% |
| **DISK+LightGlue** | **night_right** | **62.5**（中位 18） | **9.2**（中位 10） | **6.8×** | **72%** |

**v2 那个负面结果闭环了。**

v2 的判断是"不是 RANSAC 失效了，是喂给它的匹配本身就是噪声"。这一轮**只换特征和匹配器、RANSAC 判据完全不变**，跨昼夜的均值比从 1.1× 恢复到 6.8×（逐样本可分 56% → 72%，而随机是 50%）——**证实了失效在描述子，不在验证环节**。

⚠️ **两个必须保留的保留意见**：

1. **72% 仍远低于同域的 100%**，LightGlue 改善了但没有解决昼夜问题
2. **夜间分布高度偏斜**（均值 62.5，中位数只有 18）——少数配对贡献了大部分增益
3. 耗时 39 ms/对 vs ORB 的 17 ms

### 3.1 ⚠️ 混杂因素检查：分辨率不一致 ⭐

追踪单个配对时发现数据集的分辨率并不统一：

```
database/day_left        {(960, 540): 100}
query/day_right          {(960, 540): 100}
query/night_right        {(640, 360): 100}    ← 只有夜间不同，小 1.5 倍
```

**CNN 路径不受影响**（`get_default_transform` 把所有图 resize 到 224），**但几何验证是拿原图直接喂 ORB 的**——所以夜间那条路**同时有光照差和尺度失配两个变量**。"ORB 昼夜失效"这个结论有可能一部分其实是"ORB 尺度失配失效"。

**对照实验**（32 采样点，四组使用完全相同的配对）：

| 配置 | 正确均值 | 中位 | 错误均值 | 均值比 | 逐样本可分 |
|---|---:|---:|---:|---:|---:|
| **A** night 640×360（现状） | 26.4 | 26 | 25.6 | **1.03×** | **50%** |
| **B** night **上采样到 960×540** | 33.1 | 26 | 25.0 | **1.32×** | **53%** |
| **C** day_right **降到 640×360** ← 关键对照 | 83.8 | 59 | 24.5 | **3.42×** | **97%** |
| **D** day_right 960×540（上界） | 124.1 | 96 | 25.5 | **4.86×** | 88% |

**结论：混杂因素真实存在，但不是主因。**

- **C**（只施加尺度失配）：均值比 4.86× → 3.42× 确有损失，**但可分性仍是 97%——单靠尺度失配打不出"等同随机"**
- **B**（消除尺度失配、只剩光照差）：1.03× → 1.32×，可分性 50% → 53%，**仍然是在扔硬币**

> ⭐ **分辨率失配吃掉约 1.4× 的均值比，但【光照】才是让 ORB 判别力归零的主因。§3 的核心结论成立。**
>
> （D 行 88% 低于 C 行 97% 是 32 样本下的噪声，不要过度解读。）

### 3.2 单配对走查：5% 是噪声地板 ⭐

同一 query（Image004）四种配对，完全相同的流程：

| 情况 | 匹配数 | 内点数 | **内点率** |
|---|---:|---:|---:|
| 白天 · 真回环 | 774 | **347** | **44.8%** |
| 白天 · 假回环 | 469 | 26 | 5.5% |
| **夜晚 · 真回环** | 479 | **26** | **5.4%** ← 与假回环无法区分 |
| 夜晚 · 假回环 | 460 | 23 | 5.0% |

**5% 是纯随机匹配下 RANSAC 能凑出来的极限。** ±3px 的对极线带占全图约 1.3%，试 1000 次取最好落到 5% 合理。更严谨地：RANSAC 以 99% 把握抽到一次全内点样本集需要 `N = log(0.01)/log(1−w⁸)`——**w=44.8% 需约 2,800 次（可行）；w=5% 需约 10¹¹ 次，而 OpenCV 上限是 1000 次**。所以 5% 区间里 RANSAC 在数学上就不可能找到真模型，报出的内点只是最好的一次巧合。

**改进项**：`verify_pair` 已返回 `inlier_ratio`，但 `evaluate.py` 只用 `num_inliers`。**内点率不受匹配总数影响，且有 5% 这个可解释的绝对参照，是更好的判据。**

## 4. 开集评测

**协议**：从 database 移除帧号 30-49，于是 `night_right` 里 **14/100** 个 query 没有正确答案、**应该被拒绝**。

|  | 应该接受 | 应该拒绝 |
|---|---|---|
| 系统接受 | TP（且检索对） | **FP ← 灾难性的假阳性回环** |
| 系统拒绝 | FN | TN |

**Sanity check**：阈值设 0（全部接受）时 precision 应等于 R@1——三个 backbone 全部满足。

### 4.1 backbone 对比

| 配置 | R@1 | best F1 | **R@100%P** |
|---|---:|---:|---:|
| ResNet18 预训练 | 0.400 | 0.432 | **0.012** |
| ResNet18 + triplet | 0.710 | 0.796 | 0.221 |
| **DINOv2 零训练** | 0.740 | **0.874** | **0.233** |

### 4.2 DINOv2 上逐级叠加 ⭐ 一个反直觉结果

| 配置 | R@1 | best F1 | **R@100%P** |
|---|---:|---:|---:|
| 单帧 | 0.740 | 0.874 | 0.233 |
| **+ 因果序列匹配** | 0.790 | **0.912** | **0.686** |
| + 序列 + **ORB 门控** | 0.790 | 0.859 | **0.000** |
| + 序列 + **LightGlue 门控** | 0.790 | 0.849 | 0.326 |

**两个发现：**

**① 序列匹配不只改善排序，还大幅改善置信度质量**——`R@100%P` 从 0.233 到 0.686，几乎三倍。

**② 加几何验证门控反而变差。**

原因是当前实现在开启门控时，把置信度信号**从"序列匹配后的相似度"替换成了"内点数"**。而序列相似度本身就是个远好于内点数的置信度。

（LightGlue 内点数 0.326 仍明显好过 ORB 的 0.000，与 §3 的判别力测量一致。）

> ⚠️ **这是当时定位出的实现局限。** 当时的下一步判断是同时要求两个信号
> 过阈值；该实验现已完成，结果见 §4.3。
>
> 另外在真实 SLAM 里几何验证还要输出**相对位姿**送进位姿图，那个作用无法被相似度替代——所以"门控在这个指标上没赢"不等于"几何验证没用"。

### 4.3 v4 复查：联合门控实现后仍没有增益

现在已实现 validation-fitted 联合门控，并改用内点率。validation 使用
query 000-049 / exclude 30-39，test 使用 query 050-099 / exclude 70-79；
测试阶段不再扫描阈值。

| 冻结 gate | score 阈值 | 内点率阈值 | test precision | test recall | test F1 | FP |
|---|---:|---:|---:|---:|---:|---:|
| DINOv2 单帧 | 0.684 | — | 0.848 | 0.848 | **0.848** | 7 |
| sequence only | 0.792 | — | 0.958 | 0.500 | 0.657 | 1 |
| + ORB | 0.792 | 0.042 | 0.958 | 0.500 | 0.657 | 1 |
| + LightGlue | 0.792 | 0.000 | 0.958 | 0.500 | 0.657 | 1 |

结果不是预期中的提升：sequence 将 test R@1 从 0.82 提到 0.92、AUPRC 从
0.791 提到 0.947，但冻结阈值的 F1 反而从 0.848 降到 0.657——排序改善不等于
阈值更可迁移。ORB 条件被学得很宽松，LightGlue 条件直接退化为 0，两个联合
gate 都等价于 sequence-only。更重要的是，同集 oracle 的 100% precision 没有
迁移到 test，冻结阈值仍产生 1 个 FP。这说明当前真正的瓶颈是样本量与
threshold transfer，而不是缺少一个融合公式。另一个必须保留的混杂因素是：
删除连续 database 帧会压缩相似度矩阵的时间轴，使序列轨迹跨 gap 时不再满足
固定列位移假设；详见 `docs/sequence_matching.md` §8.4。

### 4.4 冻结门控下的 backbone 对比（2026-09-29 补测）⭐

§4.1 的 backbone 对比用的是 oracle best F1（在被报告的段上扫阈值），§4.3 的冻结门控只测了 DINOv2。
为了让"换特征而非加大训练"这一结论建立在可部署的数字上，用同一协议（`deploy/eval/run_protocol.sh`：
validation 000–049 / 排除库 030–039 拟合 gate → test 050–099 / 排除库 070–079 冻结应用，bootstrap 5000）
补测了两个 ResNet18。特征文件为 `outputs/v3/{base,triplet}_*.pt`，`src/evaluate.py` 未改动。

| backbone | oracle best F1（§4.1） | **冻结 gate deployed F1 [95% CI]** | FP | oracle → deployed |
|---|---:|---|---:|---:|
| ResNet18 预训练 | 0.432 | 0.347 [0.194, 0.494] | 16 | −0.085 |
| ResNet18 + triplet | 0.796 | **0.560 [0.411, 0.691]** | 8 | **−0.236** |
| DINOv2 patch-mean 零训练 | 0.874 | **0.848 [0.747, 0.926]** | 7 | −0.026 |

- oracle 口径下 DINOv2 只比微调模型高 7.8 个点；冻结门控下高 **28.8 个点**，且 95% CI **不重叠**。
  **oracle 数字低估了差距**：微调模型的阈值迁移到新路段时掉得最多（−0.236），DINOv2 几乎不掉（−0.026）。
  这与微调模型在 60 帧上的记忆（34.8 点泛化间隙）一致——它的分数分布在训练见过的段和没见过的段之间不一致
- ⚠️ 这个比较**偏向微调模型**：triplet 用夜间 000–059 做锚点训练，而测试段 050–099 与之重叠 10 帧。
  即便它见过部分测试帧，仍然大幅落后，所以结论是保守的

## 5. 当前仍缺什么

| 缺口 | 影响 |
|---|---|
| **阈值迁移能力** | validation 阈值在后半段过严，且仍需与 database-gap 混杂因素解耦（§4.3） |

| **未在标准 benchmark 跑数** | 接口已支持；仍需实际运行 MSLS / RobotCar 等数据 |

## 6. 接入真实 SLAM：KITTI 00 上的回环闭合 ⭐

前五节回答的都是"检索准不准"。这一节回答 SLAM 里真正被问的那个问题：
**回环把轨迹修正了多少。**

复现：`slam/scripts/` + `python -m src.slam_loop_closure`

### 6.1 为什么最后落在 KITTI（先在 TUM 上踩的坑）

第一版实验在 TUM `fr3_long_office_household`（RGB-D，2488 帧）上做。结果是：

| 配置 | 不开回环 | 开回环 | 改善 |
|---|---:|---:|---:|
| **RGB-D** | 1.17 cm | 1.01 cm | 13% |
| 单目 | 4.14 cm | 0.97 cm | 77% |

**RGB-D 那一行几乎没有可修的东西。** 原因是这条序列只有 24.8 m / 87 s，
而且 ORB-SLAM3 即使关掉 `loopClosing`，**局部地图复用仍然在隐式地闭环**——
相机重访旧地点时，跟踪线程直接匹配上了局部地图里的老地图点。

> ⚠️ **"关掉回环"不等于"纯里程计"。** 这是个容易想当然的地方：
> `loopClosing: 0` 只关掉了显式的回环闭合线程，没关掉地图复用。
> 在小场景里后者已经足够把漂移吸收掉。

单目那一行漂移是真的（有尺度漂移），但单目回环需要 **Sim(3)**，
而本项目的 PnP 路径给出的是度量尺度的 SE(3)——**用深度去修一条单目轨迹，
等于偷偷注入了尺度信息，对比就不干净了**。所以换到 KITTI。

### 6.2 实验设置

| | |
|---|---|
| 序列 | **KITTI odometry 00**：3709 m，4541 帧，多处回环，城郊街景 |
| 里程计来源 | ORB-SLAM3 **双目**，`loopClosing: 0` |
| 检索 | **DINOv2 ViT-S/14 + GeM**（项目的"现代"检索路径），零训练 |
| 几何验证 | **DISK + LightGlue**（项目的"现代"验证路径） |
| 相对位姿 | **双目 SGBM 深度 + PnP + RANSAC**（`src/stereo_depth.py`、`src/rgbd_pose.py`） |
| 后端 | **自己实现的高斯-牛顿位姿图**（`src/se3.py`、`src/pose_graph.py`），非 g2o/GTSAM |
| 因果约束 | 只与 **100 帧以前**的关键帧闭环，top-1 |
| 接受判据 | PnP 内点 ≥ 60 **且** 重投影误差 ≤ 1.5 px |

> ⭐ 这一步顺带补上了 Gardens Point 阶段的缺口（§3.1 记过）：那时没有内参和深度，
> 几何验证只能数内点、给不出位姿图要的那条边。KITTI 有标定和双目，两半都齐了。

### 6.3 主结果

![KITTI 00 轨迹对比](../outputs/visualizations/kitti00_loop_closure.png)

| 配置 | ATE RMSE | 最大误差 |
|---|---:|---:|
| 里程计（关闭回环） | **4.335 m** | 8.54 m |
| **本方案**（DINOv2 + LightGlue + 自建位姿图） | **1.956 m** | 3.82 m |
| DBoW2（ORB-SLAM3 原装，开启回环） | 1.204 m | 3.28 m |

**回环闭合把 ATE 降低了 55%。**

**回环边质量**（763 条，候选通过率 17.2%）：

| 指标 | 值 |
|---|---|
| 真值距离 < 5 m | **97.0%** |
| 真值距离 < 50 m | 100% |
| 距离中位数 | **0.89 m** |
| PnP 内点中位数 | 1213 |
| 重投影误差中位数 | 0.84 px |

⭐ **这是项目主线在系统级的验证**：DINOv2 在 KITTI 上的检索判别力其实**很弱**——
真回环对相似度均值 0.979、非回环对 0.954，**AUROC 只有 0.896，top-1 命中仅 17%**。
但两级串起来之后，接受的回环边**97% 落在 5 m 以内**。
**"召回强、精排弱，靠第二级把关"** 这个判断，在真实 SLAM 上仍然成立。

（顺带否掉一个假设：KITTI 图像是 1241×376（3.3:1），我以为 resize 成 224×224
压扁长宽比是判别力差的原因。实测**不是**——保持长宽比的 168×560 给出 AUROC 0.8952，
和压扁的 0.8960 没有差别；中心裁剪成方形反而掉到 0.7841，因为丢了上下文。）

### 6.4 ⭐ 误差归因分解：瓶颈不在检测

把回环对和相对位姿分别替换成真值，跑同一张位姿图：

| 配置 | ATE |
|---|---:|
| D 无回环边（下界） | 4.335 m |
| **A 我的回环对 + 我的 PnP 位姿（实际结果）** | **1.956 m** |
| B 我的回环对 + **真值**相对位姿 | 2.029 m |
| C **真值**回环对 + **真值**相对位姿 | 2.036 m |

**A ≤ B ≈ C。** 把检测和相对位姿都换成真值，ATE **不但没降反而略升**。

> ⭐ **结论：回环检测与相对位姿估计这两级都已经饱和，剩余的 1.96 m 全部来自
> 位姿图表述本身，与前端质量无关。**
>
> B 略差于 A 是可以解释的：真值回环边在真值坐标系里"完全正确"，
> 但里程计边是漂移的——一条刚性的完美约束和漂移链条的冲突反而更大；
> 而 PnP 位姿与里程计出自同一套局部一致的估计，彼此更"兼容"。
> 0.07 m 的差距本身也在噪声量级内。

### 6.5 ⭐ 信息矩阵：一个必须做对的细节

第一版用单位阵做信息矩阵，**即使喂 2000 条真值回环边，ATE 也只能到 3.17 m**。

原因是残差 `e = [平移(米), 旋转(弧度)]`。单位阵等于声明
"1 米的平移误差和 1 弧度的旋转误差一样糟"——**但 1 弧度是 57 度**，
在 3.7 km 的轨迹上，一个节点转错 1 度就能让下游整段甩出几十米。

改成各向异性 `diag([1,1,1,w,w,w])` 后（500 条真值回环边）：

| 旋转权重 w | ATE |
|---:|---:|
| 1（单位阵） | 3.28 m |
| 100 | 2.57 m |
| **1e4** | **1.97 m** |
| 1e5 ~ 1e7 | 1.95 ~ 1.98 m（趋于平稳） |

> 📌 另一个反直觉的观察：**回环边不是越多越好。** 同样的权重下
> 500 条真值回环边给出 1.97 m，2000 条反而退化到 2.20~2.36 m——
> 过多的刚性约束彼此冲突，把误差摊得更差。

### 6.6 ⚠️ 保留意见

| | |
|---|---|
| **和 DBoW2 的对比不是严格同条件** | ORB-SLAM3 的回环是**在线**执行的，闭环后还跑**完整 BA**（同时优化位姿和地图点）；本方案是**离线后处理**、**只做位姿图**，没有地图点。1.956 vs 1.204 的差距主要来自这里，不是检测质量（§6.4 已证） |
| **单一序列** | 只在 KITTI 00 上做过。其他序列、其他场景类型未验证 |
| **未在线** | 离线批处理，没有实时性约束下的验证 |
| **DINOv2 在街景上判别力弱** | AUROC 0.896、top-1 17%。能work完全依赖第二级几何验证。换到感知混淆更严重的场景（隧道、高速）可能不成立 |

## v2 的关键发现

### loss 与指标脱节

```
Epoch 1: loss 0.1246 | val R@1 0.8000   <- best
Epoch 2: loss 0.0308 | val R@1 0.7000
Epoch 5: loss 0.0020 | val R@1 0.3000   -> 早停
```

**训练 loss 单调降到 0.002，验证 Recall@1 单调降到 0.30。** 原来那个固定 5-epoch 的配置多训了 4 个 epoch，而这件事在只看 loss 时完全不可见。

### 序列匹配的两个对照

| 对照 | 结果 | 说明 |
|---|---|---|
| baseline 特征 + 同样的序列匹配 | R@1 = **1.000** | 这个 100% **几乎全部来自序列匹配，不是训练** |
| 打乱 query 时序后再做序列匹配 | R@1 = **0.300** | 增益确实来自时序结构，不是实现假象 |

### 几何验证：门控 vs 重排

重排模式把 R@1 从 1.000 打回 0.667。原因是两个任务难度不同——**判别"是不是同一地点"** 和 **在 Top-10 内部排序** 是两回事。Top-K 候选全是相隔几帧的近似图像，内点数无法在它们之间可靠排序。

**几何验证的正确角色是【门控】而不是【排序器】**，这也是 ORB-SLAM 的用法。
