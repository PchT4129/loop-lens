# 附录 B · 什么是计算图

> 穿插模块。"计算图"是理解 PyTorch 的枢纽概念——`no_grad()` 省显存、`.item()` 防 OOM、
> 孪生结构梯度累加，全都建立在它之上。本章用手算小例子 + 真实显存实测把它讲透。

---

## 1. 为什么需要计算图

训练 = 不断算梯度、朝反方向走一步（A1）。那**梯度怎么算出来**？

ResNet18 有 1118 万个参数，每个都要回答"增大一点 loss 会怎么变"。三种办法：

### 1.1 办法一：手工推导公式 ❌

对着网络结构用微积分推 `dL/dw` 的解析式。几十层卷积+BN+ReLU 的复合，式子长到没法看，改一下结构就要全部重推。

### 1.2 办法二：数值近似 ❌

```
dL/dw ≈ [ L(w + 0.0001) − L(w) ] / 0.0001
```

每算一个参数的梯度要跑一次完整前向。1118 万参数 = 1118 万次前向，且浮点误差大。

（**但调试时有用**，叫 gradient check，用来验证手写反向传播对不对。）

### 1.3 办法三：自动微分（Automatic Differentiation）✅

核心想法出奇朴素：

> **网络虽复杂，但由一堆极简单的运算（加、乘、卷积、ReLU）拼成。**
> **每个简单运算的导数我都知道。**
> **按链式法则把这些已知导数一环一环乘回去就行。**

前提是：**你得知道这些运算当初是怎么拼起来的**。

**这个"拼接记录"就是计算图。**

---

## 2. 计算图 = 前向时记的一本账

> **计算图是 PyTorch 在前向传播时，一边算一边偷偷记下的账本：记录每一步做了什么运算、用了哪些输入。**

前向时你以为它只在算数，其实同时在记账。调 `loss.backward()` 时它翻开账本**倒着走一遍**，把梯度算出来。

---

## 3. 手算一个最小例子

```
x = 2      （常量，比如输入数据）
w = 3      （参数，要求它的梯度）

a = w * x   = 6
b = a + 1   = 7
L = b * b   = 49
```

### 3.1 前向时记下的图

数据从左往右流：

```
   w(3) ──┐
          ├─[乘法]──► a(6) ──[加1]──► b(7) ──[平方]──► L(49)
   x(2) ──┘
```

但 PyTorch 实际存的是**反向指针**——每个结果记着"是谁生出我的"：

```
L ──grad_fn──► MulBackward ──► 记着输入是 b
b ──grad_fn──► AddBackward ──► 记着输入是 a
a ──grad_fn──► MulBackward ──► 记着输入是 w 和 x
```

实测确认：

```
  x = 2.0   | requires_grad=False | is_leaf=True  | grad_fn=None
  w = 3.0   | requires_grad=True  | is_leaf=True  | grad_fn=None
  a = 6.0   | requires_grad=True  | is_leaf=False | grad_fn=MulBackward0
  b = 7.0   | requires_grad=True  | is_leaf=False | grad_fn=AddBackward0
  L = 49.0  | requires_grad=True  | is_leaf=False | grad_fn=MulBackward0
```

**每个中间结果都挂着"我是被哪种运算生出来的"标记**。`x`、`w` 是你自己创建的，不是算出来的，所以 `grad_fn=None`。

### 3.2 反向传播：倒着走账本

`L.backward()` 从 `L` 出发往回走：

**第 0 步**：`dL/dL = 1`

**第 1 步**：走 `L = b * b`
```
dL/db = 2b = 2 × 7 = 14
```

**第 2 步**：走 `b = a + 1`
```
db/da = 1
dL/da = 14 × 1 = 14
```

**第 3 步**：走 `a = w * x`
```
da/dw = x = 2
dL/dw = 14 × 2 = 28
```

验算：`L = (wx+1)²` → `dL/dw = 2(wx+1)·x = 2×7×2 = 28` ✓

实测：

```
  手算: dL/dw = 28
  PyTorch: w.grad = 28.0        ✓
  x.grad = None    (x 的 requires_grad=False，不为它算梯度)
```

**这就是反向传播的全部**：每一步只做一件极简单的事——**把当前梯度乘上这一环的局部导数，传给上游**。

---

## 4. 关键洞察：为什么图会吃显存 ⭐

看上面每一环需要什么：

| 这一环 | 局部导数 | **需要前向时的什么值？** |
|---|---|---|
| `L = b * b` | `dL/db = 2b` | **需要 b 的值（7）** |
| `b = a + 1` | `db/da = 1` | 不需要任何值 |
| `a = w * x` | `da/dw = x` | **需要 x 的值（2）** |

> ⚠️ **有些运算的反向传播，必须用到前向时的中间结果。**

乘法是典型：`a = w·x`，算 `da/dw` 就得知道 `x`。加法不用（导数恒为 1）。

**所以计算图不只记"结构"，还必须保存这些中间值。**

真实网络里**卷积层就是乘法**：`y = W ⊛ x`，算权重 `W` 的梯度必须保留输入激活 `x`。ResNet18 几十层，每层的输入激活都得留着。

### 4.1 实测：这要花多少显存

batch=16 跑一次前向：

```
    with torch.no_grad()  峰值显存:   108.2 MB
    不加 no_grad()        峰值显存:   344.0 MB
                          ─────────────────────
    差额（计算图存的中间激活）: 235.8 MB   →  3.2 倍
```

> 📌 **M3 那个问题到这里彻底讲通了**：
>
> **为什么推理要加 `torch.no_grad()`？** 推理不需要反向传播，账就不用记。不记账 = 不保存中间激活 = **显存降到 1/3**。
>
> 也解释了"训练时 batch=16，推理时能 batch=64"——推理省下的正是这部分。

## 5. PyTorch 里的三个概念

### 5.1 `requires_grad` —— 要不要为它算梯度

模型参数（`nn.Parameter`）默认 `True`；输入数据默认 `False`（你不需要对输入图像求导）。

**传染性**：只要运算的输入里有任何一个是 `True`，输出就是 `True`。所以 `a = w * x` 的 `a.requires_grad` 也是 `True`。**这就是图能从 loss 一路连回参数的原因。**

### 5.2 `grad_fn` —— "我是被谁生出来的"

指向产生这个 tensor 的运算。`MulBackward0` 就是"乘法的反向函数"。

**`grad_fn` 是图的骨架**——从 `loss.grad_fn` 出发能一路回溯到所有参数。

### 5.3 `is_leaf` —— 叶子节点

**叶子 = 你自己创建的、不是任何运算结果的 tensor。** 模型参数都是叶子。

**为什么重要**：`backward()` 只把梯度填进**叶子节点**的 `.grad`。中间结果（`a`、`b`）的梯度算完就丢，不占地方——你只需要更新参数，不需要知道"第 7 层第 3 个激活的梯度"。

## 6. 实测：为什么 `.item()` 是必须的

```python
loss = crit(...)
print(loss.grad_fn)    # MeanBackward0   ← 它挂着整张计算图！
```

`loss` 不是数字，**是一个 tensor，通过 `grad_fn` 引用着整张计算图**（含那 235 MB 中间激活）。

写 `total_loss = total_loss + loss` 的后果：只要 `total_loss` 还引用着这些 loss，**每次迭代的整张图都不能释放**。

实测显存增长（batch=8，每次 3 个 forward）：

```
  循环数 │ total += loss (错)  │ total += loss.item() (对)
  ───────┼────────────────────┼──────────────────────────
     1   │    515.4 MB        │    515.4 MB
     2   │   1015.7 MB        │    515.5 MB
     4   │   2016.2 MB        │    515.5 MB
     8   │   4017.2 MB        │    515.5 MB
    16   │   8019.2 MB        │    515.5 MB
```

**左列每多一次循环多约 500 MB，完全线性。右列纹丝不动。**

> 写这个测试脚本时最初循环了 50 次，**真的把 GPU 跑 OOM 了**，PyTorch 报"已分配 27.66 GB"。这不是理论风险。

**`.item()` 做的事**：取出数值变成纯 Python `float`，**不引用任何图**，上一次迭代的图立刻可被回收。

> 📌 **通用法则**：**凡是只想要"数值"用来打印、记录、统计的地方，一律加 `.item()` 或 `.detach()`。**
> 只要一个 tensor 还挂着 `grad_fn`，你就是在攥着一整张图不放。

---

## 7. 图是"一次性"的

```python
loss.backward()
loss.backward()    # ❌ RuntimeError: Trying to backward through the graph a second time
```

**`backward()` 跑完，图默认被释放。** 因为绝大多数情况只需反向一次，用完立刻释放能省大量显存。

确实需要反向两次（GAN、多 loss 分别回传）时写 `loss.backward(retain_graph=True)`。

这解释了训练循环的节奏：

```
前向 → 建图 → 算 loss → backward（用掉图并销毁）→ 更新参数 → 下一轮重新建图
```

**每个 iteration 都在重新建一张全新的图。**

---

## 8. 动态图 vs 静态图

| | **动态图（PyTorch）** | **静态图（TensorFlow 1.x）** |
|---|---|---|
| 何时建图 | **每次前向时现场构建** | 先定义完整图，再灌数据执行 |
| 能否用 `if`/`for` | 能，图结构每次可以不同 | 不能直接用，需 `tf.cond` 等算子 |
| 调试 | 能直接 `print`、打断点、单步 | 困难，运行时看不到中间值 |
| 优化空间 | 较小（每次重建） | 较大（可整图优化） |

PyTorch 的 **define-by-run**（边跑边定义）是它当年赢下研究社区的主要原因——**你写的就是普通 Python**。

（现在两边在收敛：PyTorch 有 `torch.compile` 把动态图捕获成静态图优化；TF 2.x 默认也改成动态图。）

## 9. 回到本项目

```python
anchor_features   = model(anchor)      # 建图 ①
positive_features = model(positive)    # 建图 ②
negative_features = model(negative)    # 建图 ③

loss = criterion(a_f, p_f, n_f)        # 三张图在这里汇合成一张

optimizer.zero_grad()
loss.backward()                        # 从 loss 倒着走完整张图；走完销毁
optimizer.step()
```

**三次 forward 建了三张子图**，它们的叶子节点是**同一批参数**。`criterion` 把三个输出合成一个 loss，三张子图合并成一张 DAG。

`backward()` 从 loss 出发**沿三条路径分别回流**，梯度在共享参数处累加——正是 A1 §8 讲的事。现在你知道怎么实现的了：**图记录了三条路径，反向时自然走三遍**。

## 10. 面试怎么答

### Q1：什么是计算图？

> 是 PyTorch 在前向传播时一边算一边记录的一本账，记下每一步做了什么运算、输入是哪些 tensor。它的作用是支撑自动微分——网络虽然复杂，但由一堆简单运算拼成，每个简单运算的导数是已知的，只要知道它们怎么拼的，就能按链式法则一环一环把梯度乘回去。
>
> 具体在 PyTorch 里，每个由运算产生的 tensor 都有一个 `grad_fn` 指向生成它的反向函数，从 loss 的 `grad_fn` 出发能一路回溯到所有参数，这就是图的骨架。

### Q2 ⭐：为什么计算图会占显存？

> 因为很多运算的反向传播需要用到前向时的中间值。最典型的是乘法：`a = w·x`，要算 `da/dw` 就必须知道 `x` 的值。卷积本质也是乘法，所以每一层的输入激活都必须保存下来，等反向时算权重梯度用。
>
> 我在自己项目上测过，ResNet18 batch=16 跑一次前向，加 `no_grad()` 峰值显存 108 MB，不加是 344 MB，差出来的 236 MB 就是这些中间激活，**是 3.2 倍**。这也是为什么推理必须加 `no_grad()`，以及为什么推理能跑比训练大得多的 batch。

### Q3 ⭐：为什么累加 loss 要用 `.item()`？

> 因为 `loss` 不是一个数字，它是个 tensor，而且通过 `grad_fn` 引用着生成它的整张计算图。写 `total += loss` 的话，只要 `total` 还持有这些引用，每一次迭代的图都释放不掉。
>
> 我实测过，循环累加时显存完全线性增长——1 次 515 MB，2 次 1015 MB，16 次 8019 MB，一次约 500 MB。第一次写测试脚本循环 50 次直接把 GPU 跑 OOM 了。`.item()` 把数值取成纯 Python float，不引用任何图，上一次的图立刻能被回收。通用法则是：只要你只想要数值用于打印或统计，就加 `.item()` 或 `.detach()`。

### Q4：`backward()` 能调用两次吗？

> 默认不行，会报 "Trying to backward through the graph a second time"，因为图在第一次反向后就被释放了——绝大多数场景只需反向一次，及时释放能省大量显存。确实需要反向两次的话（比如 GAN 或多个 loss 分别回传）要传 `retain_graph=True`。

### Q5：动态图和静态图的区别？

> 动态图是每次前向时现场构建，所以可以用普通的 Python 控制流，`if`、`for`、`while` 都行，图的结构每次可以不一样，而且能直接 print 和打断点调试。静态图是先把图定义完整再灌数据执行，调试困难但整图优化空间更大。PyTorch 的 define-by-run 是它赢下研究社区的主要原因。现在两边在收敛，PyTorch 有 `torch.compile` 能把动态图捕获成静态图优化，TF 2.x 默认也改成动态图了。
