## 0. 使用纪律：怎么讲才不会变成自曝其短

### 0.1 为什么讲缺陷反而加分

面试官心里有个隐含评分维度：**这个人知不知道自己方法的边界在哪。**

- 只报好数字 → 要么没深究，要么在藏
- 能说出"我的方法在 X 下失效，原因是 Y，修法是 Z" → **三重能力**：批判性思维、机制级理解、工程判断

现实考量：**缺陷本来就会被问出来。主动说和被挖出来，观感天差地别。**

### 0.2 三条纪律

**① 顺序：先价值，再缺陷，最后修法。**

- ❌ "我这项目问题挺多的，过拟合、没做增强、BN 也有问题……"
- ✅ "严格 held-out 上 R@5 从 76.7% 到 100%，说明候选召回能力真泛化了。**但我也定位到几个明确问题**，最主要的是……**如果继续做我会先……**"

**② 每个缺陷必须带"量化"和"修法"。**

"有点过拟合"是废话。"训练前间隙 1.4 点、训练后 34.8 点，这 33 点是训练造出来的"是分析。

**③ 划清影响范围。**

指出问题后补一句"但这不影响我报告的结论，因为……"。显示你**评估过严重性**，而非慌乱地承认一切。

## 1. 陷阱一：过拟合，以及"为什么召回泛化、精排不泛化"

### 1.1 证据链

| Recall@1 | 训练区间 000-069 | held-out 070-099 | 间隙 |
|---|---:|---:|---:|
| 训练前（baseline） | 0.5143 | 0.5000 | **1.4 点** |
| 训练后（triplet） | 0.9143 | 0.5667 | **34.8 点** |

第一行的作用是**基准对照**：证明两区间难度相当。所以第二行的 34.8 点可归因于训练。

**根本原因**（A3 §2）：1118 万参数 : 70 样本 ≈ 16 万 : 1。

### 1.2 但真正值得讲的是这个 ⭐

> **为什么 R@5 完全泛化（76.7% → 100%），R@1 却几乎没泛化（+6.7 点）？**

如果只是"过拟合"，R@5 应该一起垮。所以需要更细的解释。

**模型学到的东西分两层：**

**可迁移层：昼夜之间的系统性外观变换。**

夜晚相对白天：整体亮度更低、色温偏移、光源从漫射变点光源、对比度分布改变。**这是对整条路线都成立的全局变换**，与具体在哪一帧无关。

模型学到它之后对没见过的 070-099 同样有效——能把正确答案从"排不进前 10"拉进"前 5"。**这是 R@5 打满的来源。**

**不可迁移层：具体地点的独有细节。**

要在 ±3 帧内**精确排到第一**，需要区分几乎一样的相邻帧（`Image070` vs `Image073`）。这靠每个地点的独有细节，模型只能通过**记住这 70 帧**做到，换 30 帧失效。**这是 R@1 只涨 6.7 点的原因。**

**类比**：

> 学会了"这类选择题能把答案缩到 2-3 个选项"——**可迁移的解题策略**，换卷子照样管用。
> 但没学会"这道题选 B"——那需要**具体知识**，只能靠背。

### 1.3 这个分析为什么值钱

它把结论从"我的方法过拟合了"（负面）升级为：

> **"我的方法学到的是可迁移的域变换能力，而非地点的精确判别能力。而 VPR 在 SLAM 中的职责恰好是候选召回而非最终精排——所以这个能力边界是可用的。"**

**同一组数据，从"承认失败"变成"刻画能力边界"。**

## 2. 陷阱二：database 没有按 split 切 ⚠️

### 2.1 问题

`src/triplet_dataset.py:44-51`：

```python
self.anchor_paths = [p for p in find_images(anchor_dir)
                     if (min_index is None or idx(p) >= min_index)
                     and (max_index is None or idx(p) <= max_index)]     # ← anchor 过滤了

self.database_paths = find_images(database_dir)                          # ← database 没过滤！
```

枚举训练时（`--min-index 0 --max-index 69`）实际碰到的 database 图：

```
database 被当作【正样本】的 index 范围: 0 - 72
database 被当作【负样本】的 index 范围: 0 - 99

测试区间 070-099 的 30 张 database 图：
  被当过正样本的: [70, 71, 72]
  被当过负样本的: 全部 30 张
  完全没被碰过的: 无
```

> **测试区间的 database 图，一张都没能幸免。**

### 2.2 但要讲得成熟：它部分可辩护

**辩护方**：VPR 实际部署里 **database 本来就是训练时全部可见的**——先建好地图再拿它定位。这叫 **transductive（直推式）** 设定，检索任务里很常见。真正不能泄漏的是 **query**，而 `night_right` 070-099 **确实一次都没进过训练**。

**但边界处是实打实的泄漏**：

```
day_070/071/072  被当作 night_067/068/069 的【正样本】拉近了
                     ↑
              而 night_070（测试 query）和 night_067-069 是相邻帧，画面几乎一样
```

**等于模型被间接训练成"把 day_070 放在 night_070 附近"。** 这就不是 transductive 那么无辜了。

### 2.3 成熟答法

> "我的 database 没按 split 过滤，训练时全部 100 张都用上了。这一点部分可辩护——VPR 实际部署就是先建图再定位，database 全可见是合理的直推式设定，而且测试 query 确实一次都没进过训练。
>
> **但边界处有实质泄漏**：day_070 到 072 被当作 night_067 到 069 的正样本拉近过，而这几帧和测试 query night_070 几乎是同一画面。所以测试集开头那几帧的成绩偏乐观。
>
> 修法两个：一是 database 也按区间过滤，二是训练和测试之间留一段 gap 丢掉，即 purged split。"

> 📌 **价值**：你**既没装作没问题，也没过度自我否定**，而是精确划出"哪部分合理、哪部分有问题、影响多大"。资深工程师的思考方式。

### 2.4 修法

```python
# triplet_dataset.py：让 database 也支持区间过滤
self.database_paths = [p for p in find_images(database_dir)
                       if (db_min is None or idx(p) >= db_min)
                       and (db_max is None or idx(p) <= db_max)]

# 训练时：--db-max-index 66   （留 67-69 作 gap）
# 测试时：database 用全量（部署时本就全量可见）
```

## 3. 陷阱三：随机负样本，24% 零梯度

M6 §9 已量化：

| 采样策略 | 平均 loss | loss=0 比例 |
|---|---:|---:|
| 随机负样本（当前实现） | 0.0954 | **24%** |
| 最难负样本 | 0.1685 | **1%** |

训练推进后该比例持续上升——**loss 曲线漂亮地降下去，其实是越来越多三元组在空转。**

### 3.1 修法三档

```python
# 档位一：batch-hard —— 最简单
# 对 batch 里每个 anchor，从本 batch 所有 negative 里挑离它最近的
d = torch.cdist(anchor_feat, negative_feat)      # [B, B]
hardest = d.argmin(dim=1)
loss = criterion(anchor_feat, positive_feat, negative_feat[hardest])

# 档位二：semi-hard（FaceNet 做法，更稳）
# 挑"比 positive 远，但仍在 margin 之内"的负样本：
#   d(a,p) < d(a,n) < d(a,p) + margin
# 既有梯度信号，又不至于极端

# 档位三：离线挖掘（NetVLAD 做法）
# 每隔 N 个 epoch 用当前模型给全库重抽特征，
# 为每个 anchor 缓存最难的若干负样本，下个周期从缓存里采
```

> ⚠️ **必带的补丁**：不能无脑挑最难的。最难的负样本很可能是**标注噪声**，或**本来就该相似**的东西（帧号差刚好 20、物理上还很近）。硬逼模型推开它们会导致训练崩溃。所以实践用 semi-hard。

## 4. 陷阱四：BatchNorm 域污染 ⭐ 技术含量最高

### 4.1 问题在哪

```python
anchor_features   = model(anchor)      # anchor 全是【夜间】图
positive_features = model(positive)    # positive 全是【白天】图
negative_features = model(negative)    # negative 全是【白天】图
```

M3 讲过：`train()` 模式下 BN 用**当前 batch 的均值方差**归一化。而这三次 forward 每次的 batch 都是**域纯净**的。

### 4.2 三重危害（每重都有实测）

#### 危害一：anchor 和 positive 用了两个不同的归一化函数

夜间 batch 算出一套统计量、白天 batch 算出另一套，**两个分支的输出根本不在同一个空间**——但 loss 却在算它们之间的距离。

实测（三批图拼成一个 batch 一次 forward = 正确做法，对比分三次）：

```
anchor(夜)     分开 vs 拼一起 的特征余弦: 0.8655
positive(昼)   分开 vs 拼一起 的特征余弦: 0.9186
negative(昼)   分开 vs 拼一起 的特征余弦: 0.9036
```

**同样的图像，仅因 forward 的分组方式不同，anchor 特征就差了 0.13 的余弦。**

再看 loss 真正关心的量：

```
分开 forward  : d(a,p)=0.713  d(a,n)=0.750  →  距离差 = +0.0370
拼一起 forward: d(a,p)=0.843  d(a,n)=0.889  →  距离差 = +0.0459
```

**训练信号差了 24%。** 梯度里相当一部分在响应"BN 分组方式"这个与任务无关的因素。

**对照组**（`eval()` 模式，BN 用固定 running stats）：

```
anchor 分开 vs 拼一起 的特征余弦: 1.000000   ← 完全一致，不受分组影响
```

**证明问题来源就是 BN。**

#### 危害二：running stats 被三批不同域的数据轮流拉扯

一个训练 step 内，第一层 BN 的 `running_mean`：

```
经过 anchor(全夜间)   后变化 L2 = 0.2493
再经过 positive(全昼) 后变化 L2 = 0.2793
两次更新方向的余弦   = -0.2367     ← 负数
```

**余弦为负，说明两次更新在朝相反方向拉。** 最终收敛的 running stats 是个"三不像"——既不代表夜间分布，也不代表白天分布。

而**推理时用的正是这套统计量**。

#### 危害三：train/test 行为不一致

训练时用域纯净 batch 的统计量，推理时用那套被拉扯出来的 running stats。**模型训练时经历的归一化，和部署后经历的归一化不是同一件事。**

### 4.3 修法

**方案 A（推荐）：拼成一个 batch**

```python
x = torch.cat([anchor, positive, negative], dim=0)     # [3B, 3, 224, 224]
features = model(x)
a_f, p_f, n_f = features.chunk(3, dim=0)
loss = criterion(a_f, p_f, n_f)
```

三个好处：① BN 看到昼夜混合分布，统计量有意义 ② 三分支用同一套归一化，输出在同一空间 ③ **顺带更快**——一次 forward 比三次 GPU 利用率高。

**方案 B：冻结 BN**

```python
for m in model.modules():
    if isinstance(m, nn.BatchNorm2d):
        m.eval()        # 始终用预训练的 running stats
```

小数据微调时的**常见做法**——batch=16 算出的统计量本身噪声就大，不如信任 ImageNet 上 128 万张图统计出来的那套。

> 📌 **这是整个项目里技术含量最高的发现**。需要同时理解 BN 的 train/eval 差异（M3）、triplet 三分支结构（M6）、以及数据的域构成。**能讲清楚它，基本可以确定你不是调包侠。**

## 5. 陷阱五：loss 下降 ≠ 检索变好

训练循环**只打印 loss，从不评测检索指标**：

```python
print(f"Epoch {epoch + 1}/{args.epochs} - loss: {average_loss:.4f}")
```

三个问题叠加：

1. **loss 被零梯度三元组拉低**——24% 的三元组 loss 恒为 0，把平均值往下拽，看起来像"学得好"
2. **loss 衡量"margin 满足程度"，不是"排序质量"**——把正样本拉进 margin 就停，不保证排第一
3. **没有验证集**，想评测也没有干净数据

### 5.1 修法

```python
for epoch in range(args.epochs):
    loss = train_one_epoch(...)
    recall = evaluate_on_val(model, val_loader)       # ← 补这一行
    print(f"epoch {epoch}: loss={loss:.4f}  R@1={recall:.4f}")
    if recall > best:                                  # ← 模型选择
        best = recall
        save_checkpoint()
```

> **所有修法里最基础、最该先做的一条。** 没有它，连"5 个 epoch 是不是太多"都无法回答。

## 6. 陷阱六：缺失的正则化

完整诊断表见 A3 §8。三条主要缺口：

| 缺什么 | 为什么对症 |
|---|---|
| **数据增强** | **昼夜任务最该加 `ColorJitter`**（亮度/对比度/饱和度/色相抖动），它模拟的正是光照变化。此外可加随机裁剪、轻微旋转 |
| **weight decay** | Adam 默认 `weight_decay=0`，完全没有 L2 正则。要加应换 **AdamW**（A1 §6.5） |
| **冻结浅层** | 1118 万参数全部可训练，而浅层学的是边缘/纹理等通用特征，本不需要为昼夜任务改动。冻结 `conv1`~`layer2` 能大幅降低有效容量 |

```python
# 冻结浅层
for name, p in model.named_parameters():
    if not (name.startswith("backbone.6") or name.startswith("backbone.7")):  # layer3/layer4
        p.requires_grad = False
optimizer = torch.optim.AdamW(
    [p for p in model.parameters() if p.requires_grad], lr=1e-4, weight_decay=1e-4)

# 数据增强（只对训练用，抽特征时仍用 get_default_transform）
train_tf = transforms.Compose([
    transforms.Resize((224, 224)),
    transforms.ColorJitter(brightness=0.4, contrast=0.4, saturation=0.4, hue=0.1),
    transforms.RandomHorizontalFlip(p=0.0),   # ⚠️ VPR 慎用翻转：会破坏左右空间语义
    transforms.ToTensor(),
    transforms.Normalize(mean=[0.485, 0.456, 0.406], std=[0.229, 0.224, 0.225]),
])
```

> ⚠️ **水平翻转对 VPR 要谨慎**：翻转后"左边有楼、右边有树"变成"左边有树、右边有楼"，而这个左右关系正是区分地点的线索之一。分类任务可以随便翻，VPR 不行。**这个细节能体现你在思考任务特性而不是套模板。**

## 7. 陷阱七：评测代码的静默失效

M5 §7 已展开。要点：

- `--top-k` 小于 `recall_ks` 最大值时，切片被**静默截断**，输出错误数字但不报错
- 实测：`--top-k 1` 时三个 recall 全变成 0.51，`precision@5` 变成 0.102
- **已确认所有报告的数字都是 `--top-k 10` 跑的，结论有效**

```python
assert args.top_k >= max(recall_ks), f"--top-k 必须 ≥ {max(recall_ks)}"
```

## 8. 修复优先级（按"收益 ÷ 成本"排序）

| 优先级 | 修什么 | 成本 | 预期收益 |
|---|---|---|---|
| **1** | 训练循环加**验证集评测 + 早停 + 模型选择** | 低 | **最高**——没它就是盲飞 |
| **2** | 三次 forward → **拼成一个 batch** | 极低（3 行） | 高，且**顺带加速** |
| **3** | 加**数据增强**（ColorJitter 为主） | 低 | 高，最对症昼夜任务 |
| **4** | **hard negative mining**（semi-hard） | 中 | 高，解决 24% 空转 |
| **5** | database 按 split 过滤 + **purged gap** | 低 | 中——让结论更可信 |
| **6** | 换 **AdamW + weight decay** | 极低 | 中 |
| **7** | **冻结浅层**，只训 layer3/4 | 低 | 中 |
| **8** | 换 **GeM 池化**（M2 §6.3） | 低（3 行） | 中——提升而非修 bug |
| **9** | 评测代码加 `assert` | 极低 | 低（防未来踩坑） |

> 被问"给你两周继续做，先做什么"——**照前四条说**，并说明顺序理由：**先建立可观测性（1），再改最便宜的（2），再改最对症的（3、4）**。

## 9. 面试怎么答

### Q1 ⭐：你这个项目有什么不足？

**30 秒版本：**

> "主要三块。**第一是过拟合**，我量化过：训练前训练区间和 held-out 的差距只有 1.4 个点，训练后变成 34.8 个点，这 33 点完全是训练造出来的。根本原因是 1118 万参数对 70 个样本，而且我没做数据增强、没有 weight decay、也没有验证集做早停。
>
> **第二是三元组采样太弱**，负样本随机选，我实测训练刚开始就有 24% 的三元组 loss 已经是 0、完全不产生梯度，训练在部分空转，应该上 semi-hard negative mining。
>
> **第三是一个比较隐蔽的 BatchNorm 问题**——anchor 全是夜间图、positive 和 negative 全是白天图，分三次 forward，等于每次让 BN 面对一批域纯净的数据。我测过，同样的图拼成一个 batch 一次 forward 和分三次相比，anchor 特征余弦只有 0.87，训练信号差 24%。修法很简单，cat 成一个 batch，还顺带更快。"

### Q4 ⭐：BatchNorm 那个问题具体是怎么回事？

> `train()` 模式下 BN 用当前 batch 的均值方差做归一化。我的 anchor 全是夜间图、positive 和 negative 全是白天图，分三次 forward，等于每次 BN 面对的都是一批域纯净的数据，算出的统计量完全不同。
>
> 危害有三层。**第一**，anchor 和 positive 实际上被两个不同的归一化函数处理，输出不在同一个空间，但 loss 却在算它们的距离——我实测拼成一个 batch 一次 forward 和分三次相比，anchor 特征余弦只有 0.8655，而 loss 真正关心的距离差从 0.0370 变成 0.0459，差了 24%。作为对照，在 `eval()` 模式下这个余弦是 1.000000，证明问题来源就是 BN。
>
> **第二**，running stats 被三批不同域的数据轮流更新，我测过一个 step 内两次更新方向的余弦是 −0.2367，在互相拉扯，最终得到的统计量既不代表夜间也不代表白天，而推理时用的正是它。**第三**是 train/test 行为不一致。
>
> 修法两个：把三批 cat 成一个 batch 一次 forward，这样 BN 看到混合分布、三个分支共用一套归一化，而且更快；或者直接冻结 BN 用预训练的 running stats——小数据微调时这是常见做法，因为 batch=16 算出的统计量本身噪声就大。

### Q6：你怎么知道训练是有效的？

> 说实话，我现在**不能完全确定**——训练循环里只打印了 loss，没有每个 epoch 评测检索指标。而 loss 下降本身是不可靠的信号：一是 24% 的三元组 loss 恒为 0，会把平均值拽低；二是 loss 衡量的是 margin 满足程度，不是排序质量。我只有训练结束后的一次性评测。
>
> 这是我优先级最高的改进项——加验证集、每个 epoch 评测 Recall@K、按验证指标做早停和模型选择。没有这个，我连"5 个 epoch 是不是太多"都回答不了。
