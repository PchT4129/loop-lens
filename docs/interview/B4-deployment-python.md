# Part 1 · 模型部署

## 1. 训练 vs 部署

| | 训练 | 部署 |
|---|---|---|
| 关心什么 | 吞吐 | **延迟** |
| batch | 大（16~256） | 常常是 **1** |
| 精度 | FP32 / 混合精度 | **FP16 / INT8** |
| 硬件 | A100/4090 | Jetson、手机、CPU |
| 需要反向传播 | 是 | **否** |

> 📌 **"不需要反向传播"是所有部署优化的前提。** 训练时为 backward 要保留计算图和中间激活（A2），推理全不需要——**很多训练时不能做的变换，推理时都能做。**

---

## 2. Conv + BN 融合 ⭐

**推理时 BN 用固定的 running stats**，整个 BN 就是常数线性变换：

```
y = γ·(x − μ)/√(σ²+ε) + β  =  a·x + b        ← a, b 都是常数
```

**Conv 也是线性的，两个线性变换可以合并。**

```python
scale = bn.weight / torch.sqrt(bn.running_var + bn.eps)
fused.weight = conv.weight * scale.reshape(-1, 1, 1, 1)
fused.bias   = (conv.bias − bn.running_mean) * scale + bn.bias
```

实测：

```
融合前后输出最大差异: 2.623e-06   → 数值上完全等价 ✓
参数量: 4672 (Conv 4608 + BN 64) → 4640
ResNet18 共有 20 个 BatchNorm 层，全部可以被融合掉
```

**收益不在参数量**（只少 32 个），**而在少了 20 次 kernel launch 和 20 轮显存读写**。现代 GPU 上小算子的启动开销和内存带宽往往比计算本身更贵。

> 📌 **"算子融合"最经典的例子**，TensorRT / ONNX Runtime 自动做，PyTorch 里是 `torch.ao.quantization.fuse_modules`。
>
> **只在推理时成立**——训练时 BN 用 batch 统计量、每步都变，没法融合。**又回到"不需要反向传播"这个前提。**

## 3. 量化

| 精度 | 位数 | 相对大小 | 典型损失 |
|---|---|---|---|
| FP32 | 32 | 1× | 基准 |
| **FP16 / BF16** | 16 | **1/2** | 几乎无损 |
| **INT8** | 8 | **1/4** | 通常 1% 以内（需校准） |
| INT4 | 4 | 1/8 | 明显，主要用于 LLM |

**为什么能量化**：权重分布**高度集中**（大部分接近 0），不需要 FP32 的动态范围；且网络对权重微小扰动**天然鲁棒**（与 A3"平坦极小点泛化更好"相通）。

### 3.1 在本项目上实测 FP16

```
模型权重大小: FP32 42.64 MB → FP16 21.32 MB   (2.0×)
batch=32 推理: FP32 9.44 ms → FP16 5.60 ms    (1.69× 加速)

检索指标:
精度   | day_right R@1/R@5    | night_right R@1/R@5
FP32  | 0.9600 / 1.0000      | 0.5100 / 0.7400
FP16  | 0.9600 / 1.0000      | 0.5200 / 0.7400

FP32 与 FP16 抽出的特征，平均余弦相似度 = 0.999998
```

> **模型小一半、快 1.69 倍，检索指标几乎不动。**

⚠️ **诚实说明**：night_right 0.5100→0.5200 **不是提升**——100 个 query 差 1 个，是噪声。**正确结论是"没有可测量的损失"**。特征余弦 0.999998 才是真正的证据。

### 3.2 INT8 的三种做法

| 做法 | 说明 | 精度 | 成本 |
|---|---|---|---|
| **动态量化** | 权重预量化，激活运行时统计 | 中 | **最省事**，一行代码 |
| **静态量化 PTQ** | 用**校准数据**统计激活范围，全部预量化 | 好 | 需几百张校准图 |
| **量化感知训练 QAT** | 训练时模拟量化误差 | **最好** | 要重训 |

**校准（calibration）**：跑几百张代表性数据统计每层激活范围，据此确定 scale 和 zero-point。**校准数据分布必须和真实场景一致。**

> 💡 **对本项目的具体提醒**：要量化部署的话，**校准数据必须包含夜间图像**。只用白天图校准，夜间的激活范围会超出量化区间被截断，性能会崩。**这是"校准分布要匹配"的一个真实例子。**

## 4. 部署技术路线

```
PyTorch 模型
    │
    ├─► torch.compile          最省事，PyTorch 2.x 原生，图优化 + 算子融合
    │
    ├─► TorchScript            trace/script，脱离 Python（正被 compile 取代）
    │
    ├─► ONNX ──► ONNX Runtime  【中间表示】跨框架、跨硬件的通用格式
    │      │
    │      └──► TensorRT       NVIDIA 专用，最快
    │
    └─► 移动端: TFLite / NCNN / MNN / CoreML
```

**ONNX 的定位**：它是**中间表示（IR）**，不是运行时。作用是"各种框架导出 → 各种引擎读取"，解耦训练框架和部署平台。

**TensorRT 为什么最快**：针对具体 GPU 型号做 **kernel auto-tuning**——同一个卷积试多种实现挑最快的固化。代价是**引擎文件绑定硬件和版本**，换卡要重编译。

**trace vs script**（常见追问）：
- `trace`：跑一遍记录算子，**丢失控制流**（`if` 只记录走到的那条分支）
- `script`：解析 Python 源码，**保留控制流**，但支持语法有限

## 5. 其他优化

| 手段 | 做什么 | 代价 |
|---|---|---|
| **剪枝** | 去掉不重要的权重/通道 | 非结构化剪枝需稀疏计算支持才有实际加速 |
| **知识蒸馏** | 大模型教小模型 | 要额外训练 |
| **算子融合** | Conv+BN+ReLU 合成一个 kernel | 无 |
| **图优化** | 常量折叠、死代码消除、内存复用 | 无 |

## 6. 延迟 vs 吞吐（高频追问）

| | 定义 | 怎么优化 |
|---|---|---|
| **延迟 latency** | 单次请求多少 ms | 减小 batch、算子融合、量化 |
| **吞吐 throughput** | 每秒处理多少张 | **增大 batch**、并发 |

> **两者经常矛盾**：增大 batch 提高吞吐（GPU 利用率高），但增加单次延迟（要等凑够一批）。

还要知道 **P99 延迟**：99% 的请求在多少 ms 内完成。**生产看 P99 不看平均**——平均 10ms 但 P99 500ms 的服务不可接受。

**对本项目**：回环检测跑在 SLAM 主循环旁，**关心延迟**（每个关键帧一次），不是吞吐。

## 7. 存储账 ⭐

```
项目           | FP32       | FP16      | INT8
模型权重        | 42.6 MB    | 21.3 MB   | 10.7 MB
1万张特征库     | 19.5 MB    | 9.8 MB    | 4.9 MB
100万张特征库   | 1953.1 MB  | 976.6 MB  | 488.3 MB
```

> 📌 **回到 M4 的结论**：大规模检索瓶颈是**内存不是计算**。
>
> 模型再压也就省几十 MB，但**特征库在百万级是 GB 量级**。**对 VPR 系统，量化特征库的收益远大于量化模型**——这正是 M4 §8.2 的 PQ 乘积量化在做的事（压缩 256 倍，比 INT8 更狠）。

# Part 2 · Python 进阶（用本项目代码当例子）

## 8. 装饰器

**本质：一个函数，吃一个函数，吐一个函数。**

```python
def timer(fn):
    @functools.wraps(fn)          # 保留原函数的 __name__、__doc__
    def wrapper(*args, **kwargs):
        t = time.perf_counter()
        r = fn(*args, **kwargs)
        print(f"[{fn.__name__} 耗时 {(time.perf_counter()-t)*1000:.2f} ms]")
        return r
    return wrapper

@timer
def work(n): ...
```

> **`@timer` 等价于 `work = timer(work)`。语法糖，没有魔法。**

**`@functools.wraps` 必须加**——不加的话 `work.__name__` 变成 `"wrapper"`，文档丢失，调试和 introspection 全乱。

### 8.1 本项目里的三个装饰器

| 装饰器 | 在哪 | 做什么 |
|---|---|---|
| `@lru_cache(maxsize=512)` | `geometric_verification.py` | 缓存函数结果 |
| `@torch.no_grad()` | `train_triplet.py::evaluate_model` | 整个函数内关闭 autograd |
| `@staticmethod` | `dataset.py::_find_images` | 不需要 `self` 的方法 |

**`@torch.no_grad()` 有意思的地方**：它**既是装饰器又是上下文管理器**——可以 `@torch.no_grad()` 装饰函数，也可以 `with torch.no_grad():`。实现继承自 `_DecoratorContextManager`。

### 8.2 `lru_cache` 的真实收益（实测）

```
场景：1 个 query 对 10 个候选做几何验证（重复 5 次取最快）

有缓存: 173.2 ms   (ORB 提取 11 次: query 1 次 + database 10 次)
无缓存: 200.5 ms   (ORB 提取 20 次: 每轮都重提 query)
缓存命中 9 次，节省 14%
```

**原理**：`verify_pair(query, db_i)` 循环调用时 **query 图被反复传入**，缓存让它的 ORB 特征只提取 1 次而非 10 次。

**候选越多省越多**；`maxsize=512` 足够装下整个 database，所以**跨 query 时 database 图也会命中**。

> ⚠️ **两个坑**：① 参数必须**可哈希**；② **缓存的是引用不是副本**——返回可变对象并被外部修改会污染缓存。

## 9. 上下文管理器

**核心价值：保证"一定会收尾"，哪怕中途抛异常。**

```python
class Timer:
    def __enter__(self):
        self.t = time.perf_counter()
        return self                        # 返回值给 as 后面的变量
    def __exit__(self, exc_type, exc_val, tb):
        print(f"[耗时..., 异常={exc_type}]")
        return False                       # False = 不吞掉异常
```

实测：

```
正常路径:  [耗时 0.37 ms, 异常=None]
抛异常时:  [耗时 0.00 ms, 异常=<class 'ValueError'>]
          异常被正常抛出到外面
```

**`__exit__` 在异常情况下依然被调用**——这就是它比 `try/finally` 更好用的地方：收尾逻辑封装进对象，调用方只管 `with`。

**`__exit__` 的返回值**：返回 `True` **吞掉异常**（危险），`False`/`None` 让异常正常传播。

> 📌 **`torch.no_grad()` 就是这么实现的**：`__enter__` 保存并关闭 grad 状态，`__exit__` **无论是否异常都恢复**。用普通函数调用来关/开的话，中间一抛异常 autograd 就永久关掉了。

`contextlib` 的简洁写法：

```python
from contextlib import contextmanager

@contextmanager
def timer():
    t = time.perf_counter()
    try:
        yield                    # yield 之前是 __enter__，之后是 __exit__
    finally:
        print(f"耗时 {(time.perf_counter()-t)*1000:.2f} ms")
```

## 10. 生成器

**两个核心价值：省内存 + 惰性求值。**

```
列表推导 [i*i for i in range(1_000_000)]  占内存: 8.1 MB
生成器   (i*i for i in range(1_000_000))  占内存: 0.0002 MB
```

**差 4 万倍。** 列表把一百万个数**全部算出来存下**，生成器只存"怎么算下一个"的状态。

### 10.1 惰性 + 短路：`evaluate.py` 用的就是这个

```python
hit = any(
    is_correct_match(query_path, database_paths[db_idx.item()], tolerance)
    for db_idx in retrieved_indices          # ← 生成器表达式，不是列表
)
```

实测：

```
any(check(i) for i in range(1000))  实际只调用了 3 次 check
→ 找到第一个 True 就停，后面 997 次根本没执行
```

> 📌 **M5 讲的"`any()` 短路求值"，底层机制就是生成器的惰性。**
>
> 写成 `any([check(i) for i in range(1000)])`（**注意方括号**）会先把 1000 个结果**全部算完**再判断——**短路完全失效**。真实存在的性能坑。

### 10.2 `yield` 与协程

函数里有 `yield` 就变成生成器函数：调用它**不执行任何代码**，只返回生成器对象；每次 `next()` 才执行到下一个 `yield` 并暂停。

**PyTorch 的 `DataLoader` 就是可迭代对象**——不会一次性造好所有 batch，而是**边训练边生产**。这是它能处理超大数据集的原因。

## 11. 面试怎么答

### Q1 ⭐：模型部署有哪些优化手段？

> 首先要意识到部署和训练最大的差别是**不需要反向传播**，这解锁了一大批优化。
>
> 最典型的是 **Conv+BN 融合**：推理时 BN 用的是固定的 running stats，整个 BN 就是一个常数线性变换 `a·x+b`，而 Conv 也是线性的，两者可以合并成一个 Conv。我验证过融合前后输出完全等价，ResNet18 有 20 个 BN 全都能融掉。收益不在参数量而在少了 20 次 kernel launch 和显存读写。
>
> 然后是**量化**。我在自己项目上测过 FP16：模型从 42.6 MB 降到 21.3 MB，batch=32 的推理从 9.44 ms 降到 5.60 ms，快 1.69 倍，而检索指标完全没变，特征余弦相似度 0.999998。INT8 需要校准，分静态 PTQ 和 QAT 两条路。
>
> 工程路线上，`torch.compile` 最省事，ONNX 是跨框架的中间表示，TensorRT 最快但会针对具体 GPU 做 kernel 调优、引擎文件绑定硬件。

### Q2：量化的校准数据怎么选？

> 校准就是跑几百张代表性数据，统计每层激活的数值范围，据此确定量化的 scale 和 zero-point。**关键是校准数据的分布必须和真实部署场景一致**。
>
> 我这个项目就是个很好的例子：如果只用白天图校准，夜间图像的激活范围会超出量化区间被截断，性能会崩。所以校准集必须同时包含白天和夜间。

### Q3：延迟和吞吐的区别？

> 延迟是单次请求从进到出多少毫秒，吞吐是每秒能处理多少张。**两者经常矛盾**——增大 batch 能提高吞吐因为 GPU 利用率上去了，但会增加单次延迟因为要等凑够一批。生产环境一般看 P99 延迟而不是平均值。
>
> 我这个项目关心的是延迟——回环检测跑在 SLAM 主循环旁，每个关键帧触发一次，不存在批量请求。

### Q4：TorchScript 的 trace 和 script 有什么区别？

> trace 是跑一遍记录实际执行的算子，所以会**丢失控制流**——`if` 分支只会记录当次走到的那一条，换个输入就错了。script 是解析 Python 源码生成 IR，**保留控制流**，但支持的 Python 语法有限。有动态控制流就必须用 script。

### Q5 ⭐：讲讲装饰器 / 上下文管理器 / 生成器。

> **装饰器**本质就是"吃一个函数、吐一个函数"，`@timer` 等价于 `work = timer(work)`。要记得加 `functools.wraps`，否则原函数的名字和文档都会丢。我项目里用了 `@lru_cache` 缓存 ORB 特征提取，实测在几何验证里省了 14%——因为一个 query 对多个候选时，query 图只需要提取一次。
>
> **上下文管理器**的核心价值是保证一定会收尾，哪怕中途抛异常 `__exit__` 也会被调用。`torch.no_grad()` 就是靠它保证退出时一定恢复 autograd 状态；它同时还是个装饰器，两种用法都支持。
>
> **生成器**是惰性求值，内存 O(1)。我测过一百万个元素，列表占 8.1 MB，生成器只占 0.0002 MB。我的评测代码里 `any(...)` 用的就是生成器表达式，实测找到第一个 True 就停，1000 次里只执行了 3 次。**注意如果写成 `any([...])` 加了方括号，会先全部算完，短路就失效了。**
