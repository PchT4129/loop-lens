# 附录 O · RAG（检索增强生成）

> 项目无关的通用主题，但**它的检索侧架构和本项目是同构的**。
> 前置：M1（漏斗结构）、M4（向量检索与索引）、A4（Recall@K）、C1（微调）。

---

## 0. 开场：本项目已经实现过它的一半

**RAG 的检索侧架构和 VPR 项目结构上完全对应**：

| 阶段 | 本项目（VPR） | RAG |
|---|---|---|
| **第①级 廉价召回** | CNN 全局描述子（512 维） | 双塔 embedding |
| 能否预计算 | **能**：database 特征离线算好 | **能**：文档向量离线入库 |
| 匹配方式 | 余弦相似度 + topk | 余弦相似度 + topk |
| 索引 | FAISS / HNSW | FAISS / Milvus / Qdrant |
| **第②级 昂贵精排** | ORB+RANSAC 几何验证 | cross-encoder 重排 |
| 能否预计算 | **不能**：必须两图配对 | **不能**：必须 query+doc 拼一起 |
| 作用 | 剔除误检 / 门控 | 精排 / 过滤 |

§5 会解释**为什么两者必然长成同一个形状**。

## 1. RAG 解决什么问题

大模型的三个硬伤：

| 问题 | 表现 |
|---|---|
| **知识截止** | 训练数据有截止日期 |
| **不知道私有知识** | 公司文档、私有代码库 |
| **幻觉** | 不知道也会一本正经地编 |

**微调能解决吗？** C1 §6：**不能，或很不划算**——微调教的是**行为和风格**不是**知识**；知识更新一次就要重训；而且模型学到的是"这类问题该这么答"，**记不住具体事实**。

**RAG 的思路**：

> **不让模型"记住"知识，而是在它回答前把相关资料找出来塞给它。**
> **从"闭卷考试"变成"开卷考试"。**

## 2. 完整流程

```
┌─────────────── 离线：建索引（做一次）───────────────┐
│  原始文档 (PDF/网页/代码)                            │
│      ↓ ① 解析、清洗                                 │
│      ↓ ② 分块 chunking                             │
│      ↓ ③ embedding 模型编码                         │
│      ↓ ④ 存进向量库                                  │
│  向量索引 (FAISS / Milvus / …)                       │
└────────────────────────────────────────────────────┘

┌─────────────── 在线：查询（每次请求）──────────────┐
│  用户问题                                            │
│      ↓ ⑤ (可选) 查询改写                             │
│      ↓ ⑥ 同一个 embedding 模型编码                   │
│      ↓ ⑦ 向量检索 Top-K                             │
│      ↓ ⑧ (可选) cross-encoder 重排                  │
│      ↓ ⑨ 拼进 prompt                                │
│      ↓ ⑩ LLM 生成                                   │
│  答案 (+ 引用来源)                                    │
└────────────────────────────────────────────────────┘
```

> 📌 **③ 和 ⑥ 必须用同一个 embedding 模型。** 道理和本项目 database/query 必须用同一个 checkpoint 抽特征完全一样——**否则两组向量不在同一空间，相似度没有意义**。

## 3. 分块（chunking）—— 最被低估的一环 ⭐

很多人以为 RAG 的关键是 embedding 模型或向量库，**实践中最影响效果的其实是分块**。

**两难困境**：

```
块太小  →  语义不完整（"如上所述，该方法……" ← 上文是啥？）
块太大  →  噪声多，embedding 被稀释，塞进 prompt 浪费 token
```

> 💡 **这和 GAP 的问题同类**（M2 §2.3）：**把太多东西平均成一个向量，判别力被稀释**。分块太大的 embedding，和 GAP 把 49 个空间位置平均掉，是同一种信息损失。

**常见策略**：

| 策略 | 做法 | 适用 |
|---|---|---|
| **固定长度 + 重叠** | 每 512 token 一块，相邻重叠 50 | 通用基线。**重叠防止关键信息被切断** |
| **按结构切** | 按标题、段落、markdown 层级 | **文档有结构时最好** |
| **语义切分** | 相邻句子 embedding 相似度低处切 | 效果好但慢 |
| **父子块** | **小块检索**（精准），返回**大块**（完整上下文） | **实践中很好用**，兼顾两头 |

**父子块直接化解了两难**：检索要小块（精准），生成要大块（完整），那就两个都留着。

## 4. 检索

### 4.1 向量检索

**就是 M4 那套**：query 编码 → 余弦相似度 → topk。规模大了同样上 **FAISS / HNSW / IVF-PQ**，**完全是 M4 §8 的三条路线**。

### 4.2 但只有向量检索不够 ⭐

**稠密检索擅长语义匹配，短板是精确匹配。**

```
用户问："ORA-01555 这个错误怎么解决？"
```

向量检索可能返回一堆"关于数据库错误的通用讨论"，**却漏掉那篇标题就叫 ORA-01555 的文档**——错误码这类**低频精确 token** 在语义空间里没有区分度。

**解法：混合检索（hybrid search）**

```
BM25（关键词/稀疏检索）  →  擅长精确匹配、专有名词、错误码
向量检索（稠密检索）      →  擅长语义、同义改写
        ↓  融合（常用 RRF: Reciprocal Rank Fusion）
```

**BM25 是传统 IR 方法**（TF-IDF 的改进版），完全不用神经网络。**在 RAG 里不但没过时，反而是标配。**

> 💡 **和 M8 的 DBoW2 同理**：传统方法在特定维度上仍有不可替代的优势，最好的系统往往是**混合**的。

### 4.3 查询改写

| 问题 | 改写 |
|---|---|
| **口语化** | 提取关键词，规范化 |
| **多轮指代**（"它的性能怎么样？"） | 补全成独立问题 |
| **过于宽泛** | 拆成多个子问题分别检索 |
| **HyDE** | 先让 LLM **编一个假答案**，用假答案去检索 |

**HyDE 反直觉但有效**：假答案内容可能是错的，但它的**语义分布更接近真实文档**（都是陈述句、都用专业术语），比原始疑问句更容易匹配上。

## 5. 重排：为什么必须两级 ⭐ 本章核心

### 5.1 两种编码方式

```
双塔 (bi-encoder):
    query  → Encoder → 向量 ─┐
                              ├→ 余弦相似度
    doc    → Encoder → 向量 ─┘
    ↑ 两边【独立】编码

交叉编码 (cross-encoder):
    [query + doc] 拼在一起 → Encoder → 一个分数
                   ↑ 两者【一起】进模型，能充分交互
```

交叉编码**精度明显更高**（query 和 doc 的每个 token 都能互相注意到），但有致命问题。

### 5.2 实测：为什么 cross-encoder 不能直接用来检索

假设一次 encoder 前向 10 ms：

```
知识库规模      | 双塔: 1次编码+向量检索 | 交叉编码: N次前向
1,000         | 10.0 ms             | 10.0 秒
100,000       | 13.4 ms             | 1000 秒
1,000,000     | 44.0 ms             | 2.8 小时
10,000,000    | 350.0 ms            | 27.8 小时
```

**根本原因：交叉编码无法预计算。**

> 双塔的文档向量可以**离线算好存起来**，在线只算 query 一次。
> 交叉编码的分数**依赖具体 query**，每来一个 query 都得**把全库重跑一遍**。

### 5.3 两级组合就可行

```
双塔从 100 万篇召回 Top-10，再对这 10 篇做交叉编码:  144 ms
双塔从 100 万篇召回 Top-50，再对这 50 篇做交叉编码:  544 ms
```

**这就是"廉价召回 + 昂贵精排"的漏斗。**

### 5.4 ⭐ 为什么和本项目同构

| | 本项目 | RAG |
|---|---|---|
| 廉价召回 | CNN 描述子，**database 特征可离线算好** | 双塔，**文档向量可离线入库** |
| 昂贵精排 | ORB+RANSAC，**必须两图配对才能算** | cross-encoder，**必须 query+doc 拼一起** |

**为什么必然长成同一个形状？** 因为面对**同一个结构性约束**：

> **精度高的方法都需要"两个东西一起看"；"一起看"意味着不能预计算；不能预计算就无法扩展到大规模。**
>
> **所以任何大规模检索系统，都必然演化成"可预计算的粗筛 + 不可预计算的精排"。**

这个洞察**跨领域通用**——图像检索、文本检索、推荐系统、人脸识别，全是这个结构。

**面试时能说出这一层，比说"RAG 就是检索加生成"高好几个段位**，而且你有亲手实现过的例子可举。

## 6. 怎么评估 RAG

**必须拆成两部分，这是关键。**

### 6.1 检索质量

**就是熟悉的那套**：`Recall@K`、`Precision@K`、`MRR`、`NDCG`。

> **A4 那套完全适用**，而且 RAG 同样**重 recall**——正确资料只要进 Top-K，LLM 就有机会用上；**没检索到后面再强也没用**。**和 M1 §1.4 的漏斗逻辑一模一样。**

### 6.2 生成质量

| 指标 | 衡量什么 |
|---|---|
| **Faithfulness 忠实度** | 答案**是否有检索到的资料支撑**（防幻觉） |
| **Answer Relevance** | 答案是否切题 |
| **Context Relevance** | 检索到的资料是否真的相关 |

**RAGAS** 是常用框架，思路是**用 LLM 当裁判**打分。

### 6.3 一个必须知道的失败模式

> **检索对了，但生成时被忽略了。**
>
> 有名的现象叫 **"Lost in the Middle"**——关键信息放在长上下文的**中间**位置时 LLM 更容易忽略，放开头或结尾则注意得到。
>
> **所以重排不只为了"选对"，也为了"把最相关的放在最前面"。**

## 7. RAG vs 微调

| | RAG | 微调 |
|---|---|---|
| 教什么 | **知识** | **行为、风格、能力** |
| 知识更新 | **改库即可，秒级** | 要重训 |
| 可解释性 | **能给出引用来源** | 黑盒 |
| 成本 | 每次请求多花 token | 一次性训练成本 |
| 延迟 | **增加**（检索 + 更长 prompt） | 不增加 |
| 适合 | 事实型问答、私有知识、时效内容 | 特定输出格式、领域语气、新能力 |

> 📌 **不是二选一，实践中常一起用**：**微调让模型学会"怎么用检索到的资料回答"（行为），RAG 提供"资料"（知识）。**

## 8. 常见问题速查

| 症状 | 可能原因 | 怎么查 |
|---|---|---|
| 答非所问 | **检索没召回**正确资料 | 先单独测**检索的 Recall@K**，别一上来调 prompt |
| 检索到了但答错 | 上下文太长 / 关键信息在中间 | 加重排，把最相关的放最前 |
| 精确名词查不到 | 只用了向量检索 | 加 **BM25 混合检索** |
| 答案不完整 | 块切得太碎 | 用**父子块**或加大重叠 |
| 幻觉 | prompt 没约束 | 明确要求"只根据资料回答，没有就说不知道" |

> 💡 **排查第一原则：先分清是"检索问题"还是"生成问题"。** 把检索单独拎出来测 Recall@K，能省掉大量瞎调 prompt 的时间。
>
> **这和本项目"先诊断瓶颈在排序还是召回，再决定做什么"是同一个方法论。**

## 9. 面试怎么答

### Q1：RAG 和微调怎么选？

> 核心区别是 **RAG 给知识、微调给行为**。如果模型是"不知道某些事实"——比如公司内部文档、时效性内容——应该用 RAG，因为知识更新只要改库，而且能给出引用来源、可解释。如果是"输出格式不对""语气不对"或者需要一种新能力，那才是微调的场景。
>
> 两者也经常一起用：微调让模型学会怎么使用检索到的资料，RAG 负责提供资料。

### Q2 ⭐：为什么 RAG 需要重排？直接用交叉编码检索不行吗？

> 不行，因为**交叉编码无法预计算**。双塔是 query 和 doc 各自独立编码，文档向量可以离线算好存进向量库，在线只需要编码 query 一次再做向量检索。交叉编码是把 query 和 doc 拼在一起进模型，分数依赖具体的 query，所以每来一个查询都要把全库重跑一遍——我算过，100 万文档、一次前向 10 ms 的话要 2.8 小时。
>
> 所以只能做成两级：双塔从百万级里召回 Top-10，再对这 10 篇做交叉编码，总共 144 ms。**这就是"廉价召回 + 昂贵精排"的漏斗。**
>
> 有意思的是，**这个结构和我做的 VPR 项目完全同构**——CNN 全局描述子是可预计算的粗筛，ORB+RANSAC 几何验证必须两张图配对、不能预计算，所以只能对 Top-K 做。**本质约束是一样的：精度高的方法都要"两个东西一起看"，而一起看就不能预计算，就无法扩展。**

### Q3：RAG 效果不好，你怎么排查？

> **第一步一定是先分清检索问题还是生成问题**，把检索单独拎出来测 Recall@K。很多人一上来就调 prompt，但如果正确资料根本没被检索到，prompt 调破天也没用。
>
> 如果是检索问题：看是不是分块策略不对——块太碎语义不完整，块太大 embedding 被稀释；看是不是需要混合检索——纯向量检索对错误码、专有名词这类精确匹配很弱，要配 BM25；还可以做查询改写。
>
> 如果是生成问题：可能是上下文太长导致关键信息被忽略，有个现象叫 Lost in the Middle，信息放中间容易被跳过，所以重排不只是选对还要排在前面；也可能是 prompt 没约束住，要明确要求只根据资料回答。

### Q4：分块要注意什么？

> 这是最被低估的一环。核心矛盾是块太小语义不完整、块太大 embedding 被稀释——后者和 CNN 里 GAP 把太多空间信息平均掉是同一种损失。
>
> 通用基线是固定长度加重叠，重叠是为了防止关键信息刚好被切断。文档有结构的话按标题层级切更好。实践中我觉得最好用的是父子块——**用小块做检索保证精准，命中后返回它所属的大块保证上下文完整**，直接化解了那个两难。

## 10. 小结

| 要点 | 内容 |
|---|---|
| **RAG 解决什么** | 知识截止、私有知识、幻觉。**闭卷变开卷** |
| **两个阶段** | 离线（解析→**分块**→编码→入库）；在线（改写→编码→检索→**重排**→拼 prompt→生成） |
| **同一 embedding 模型** | 索引和查询必须一致，**否则向量不在同一空间** |
| **分块最被低估** ⭐ | 太小语义不全，太大噪声稀释（**同 GAP 的稀释**）。**父子块**兼顾两头 |
| **混合检索** | 向量擅长语义，**BM25 擅长精确匹配**。传统方法没过时 |
| **HyDE** | 先编假答案再检索——**假答案的语义分布更接近真实文档** |
| **为什么两级** ⭐ | **交叉编码无法预计算**：100 万文档 2.8 小时；两级只要 144 ms |
| **跨领域通用洞察** ⭐ | **精度高→要一起看→不能预计算→无法扩展**。大规模检索系统**必然**是"可预计算粗筛 + 不可预计算精排" |
| **评估拆两半** | 检索用 Recall@K（**同样重 recall**）；生成看忠实度。**先分清检索问题还是生成问题** |
| **Lost in the Middle** | 关键信息在中间容易被忽略 → **重排不只为选对，也为排在前** |
| **vs 微调** | **RAG 给知识，微调给行为**。常一起用 |
