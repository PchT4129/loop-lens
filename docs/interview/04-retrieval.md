## 1. 检索到底在做什么

先忘掉代码。你手上有：

- **数据库**：100 张白天拍的图，每张已变成 512 个数字组成的向量
- **查询**：1 张夜里拍的图，也是 512 个数字

要回答：**这 100 张里，哪一张和我这张是同一个地点？**

朴素做法：**跟每一张都比一次，挑分数最高的。**

所以：

```
检索 = ① 算相似度  +  ② 挑最大的几个
```

代码里正好两行，一行干一件事：

```python
similarities = query_features @ database_features.T          # ①
top_scores, top_indices = torch.topk(similarities, k, dim=1) # ②
```

---

## 2. 两个向量之间怎么"比"

M2 里我们把每个向量的长度归一化成 1 了，这一步在这里兑现。

把每个向量想象成一支**从原点射出的箭头**。长度都是 1，尖端全落在半径为 1 的球面上。那么两张图像不像，就只剩一个衡量方式：**两支箭头的夹角**。

- 夹角 0°，cos = 1 → 完全同向，最相似
- 夹角 90°，cos = 0 → 垂直，毫不相干

线性代数的恒等式：

```
a · b = |a| × |b| × cos θ
```

因为 `|a| = |b| = 1`：

```
a · b = cos θ
```

**点积就是余弦相似度**。而点积算起来极简单——512 个数逐位相乘再全部加起来：

```
a · b = a₁b₁ + a₂b₂ + … + a₅₁₂b₅₁₂
```

> 📌 **这就是 L2 归一化的兑现点**。没有归一化要算 `a·b / (|a|·|b|)`，多两次开方一次除法；归一化后，相似度退化成一次乘加。

## 3. 一行矩阵乘法为什么等于"全部算完" ⭐

100 个 query × 100 个 database = **10000 对**相似度，代码只写了一行。为什么够？用缩小版手算一遍。

设 **2 个 query、3 个 database、向量 3 维**：

```
query (2×3)              database (3×3)
q₀ = [1,   0,   0]       d₀ = [1,   0,   0]
q₁ = [0,   1,   0]       d₁ = [0.6, 0.8, 0]
                         d₂ = [0,   0,   1]
```

转置 `database.T` 把它竖过来，**每一列变成一个 database 向量**：

```
database.T =
      d₀   d₁   d₂
    [ 1   0.6   0 ]
    [ 0   0.8   0 ]
    [ 0    0    1 ]
```

矩阵乘法的定义是：**结果[i][j] = 左边第 i 行 × 右边第 j 列（逐位相乘再求和）**。

而"左边第 i 行"就是 query i，"右边第 j 列"就是 database j，所以：

> **结果[i][j] = qᵢ · dⱼ = query i 与 database j 的余弦相似度**

手算：

```
结果[0][0] = q₀·d₀ = 1×1   + 0×0   + 0×0 = 1.0
结果[0][1] = q₀·d₁ = 1×0.6 + 0×0.8 + 0×0 = 0.6
结果[0][2] = q₀·d₂ = 1×0   + 0×0   + 0×1 = 0.0

结果 = [ 1.0  0.6  0.0 ]   ← 第 0 行 = q₀ 对所有 database 的完整成绩单
       [ 0.0  0.8  0.0 ]   ← 第 1 行 = q₁ 的成绩单
```

**矩阵乘法的定义天生就是"左边每一行 × 右边每一列"，这恰好就是"每个 query × 每个 database"。**

真实尺寸：`[100,512] @ [512,100] → [100,100]`，10000 个分数，一行代码。

## 4. 为什么不写 for 循环 —— 实测快 1489 倍

逻辑等价的写法：

```python
for i in range(100):
    for j in range(100):
        similarities[i][j] = torch.dot(query[i], database[j])
```

实测（CPU）：

```
矩阵乘法 q @ d.T      :  0.39 ms
双层 for 循环逐对点积 : 46.06 ms      → 慢 1489 倍
```

三层原因，一层比一层深：

1. **Python 解释器开销**：循环 10000 次 = 走 10000 遍解释器。`@` 只调用一次，剩下全在 C++/CUDA 里
2. **底层是 BLAS**：`@` 落到 OpenBLAS / MKL / cuBLAS，用 **SIMD**（一条指令算 8 个浮点乘法）、**分块**（让数据待在 CPU 缓存里）、**多线程**
3. **GPU 上更夸张**：几千核心并行算不同的行列组合

> 📌 这背后的通用原则叫 **向量化（vectorization）**：**把逐元素的循环改写成整块的张量运算**。这是所有 numpy/PyTorch 性能优化的第一原则，ML 工程岗高频考点。1489 这个数字是很好的记忆锚点。

## 5. `topk` 的三个要点

```python
top_scores, top_indices = torch.topk(similarities, k=5, dim=1)
```

**① `dim=1` 是在每一行内部找**

分数矩阵形状是 `[query数, database数]`。`dim=1` 指 database 那一维 → 在每个 query 的成绩单**内部**排名。写成 `dim=0` 就变成"每张 database 图最匹配哪些 query"，是另一个问题。

**② 返回两个张量，第二个才是答案**

```
top_scores  [100, 5]  → 分数多少
top_indices [100, 5]  → 是第几张 database 图    ← 这个才是答案
```

`top_indices[i][0]` = 第 i 个 query 的最佳匹配在 database 里的**下标**。拿它去 `database_paths` 查就得到路径。**整个系统靠"下标"串起来**——`evaluate.py`、`visualize.py` 都是这么用的。

**③ 它不是"全排序后取前 5"**

全排序 O(N log N)；`topk` 用部分选择算法（快速选择 / 堆），只保证前 k 个正确有序。N 大 k 小时快得多。

---

## 6. 一个防御性细节

```python
k=min(k, database_features.shape[0])
```

数据库只有 3 张图却要 top-5 时，`torch.topk` 会直接抛异常。这行把 k 截断到数据库大小。

小事，但被问"你做过哪些边界处理"时这是个**具体**的例子，比空泛说"注意了鲁棒性"强。

## 7. 规模变大先卡在哪？⚠️ 反直觉

假设不是 100 张，而是一座城市的 100 万张。大多数人第一反应是"计算量爆炸"。**先看实测**（1 个 query 对 N 张，CPU 精确搜索）：

| 数据库大小 | 检索耗时 | 特征库常驻内存 |
|---:|---:|---:|
| 1 万 | 0.14 ms | 19.5 MB |
| 10 万 | 3.71 ms | 195 MB |
| **100 万** | **33.8 ms** | **1953 MB ≈ 1.9 GB** |

**100 万张图，暴力精确搜索只要 34 毫秒** —— 对 SLAM 完全够用（回环检测不必每帧做，通常几 Hz）。

**先撞墙的是内存。**

单图存储量：512 维 × 4 字节（float32）= **2048 字节 ≈ 2 KB**。这个数很好用：

| 规模 | 原始存储 |
|---|---:|
| 100 万张 | 1.9 GB |
| 1 亿张 | **190 GB** |

机器人是嵌入式平台（Jetson 之类），总内存可能就 8 GB，还要跑 SLAM 前端、建图、控制。1.9 GB 全给特征库不现实。

> 📌 **记牢**：大规模检索的瓶颈顺序是 **先内存，后计算**。
> 很多人张口就说"要用 FAISS 加速"，更准确的说法是"要用 FAISS **压缩存储**，顺带加速"。这个差别在系统设计面里很明显。

## 8. 三条优化路线

### 8.1 路线一：降维（最简单）

512 维里有大量冗余（M2 里看到特征全非负、高度相关）。**PCA** 降到 128 维，信息损失很小：

| | 原始 | PCA→128 维 | 压缩比 |
|---|---:|---:|---:|
| 100 万张 | 1.9 GB | 0.5 GB | 4× |
| 1 亿张 | 190 GB | 47.7 GB | 4× |

而且 PCA 通常配 **whitening（白化）**——去相关 + 各主成分方差归一，往往还能**提升检索精度**。这就是 M2 说的那个"几乎免费的提升"，NetVLAD / GeM 论文都标配。

### 8.2 路线二：量化（压缩每个数字）

**最朴素**：float32 → int8，4 倍压缩，精度损失小。

**更狠的是 PQ（Product Quantization，乘积量化）**，白话版：

> 把 512 维向量**切成 8 段**，每段 64 维。
> 对每一段，事先在全库上聚类出 **256 个"代表向量"**（像调色板上的 256 个标准色）。
> 存的时候每段只记"我最像第几号代表"——一个 0~255 的编号，**正好 1 字节**。
> 8 段 = **8 字节**。原来 2048 字节 → **压缩 256 倍**。

| | 原始 | PQ（8 字节） |
|---|---:|---:|
| 100 万张 | 1.9 GB | **0.01 GB** |
| 1 亿张 | 190 GB | **0.75 GB** |

一亿张图塞进 1 GB 内存。代价是**有误差**——存的是"最像的代表向量"而非原向量，检索精度会掉一点。

### 8.3 路线三：近似最近邻 ANN（不再和所有人比）

前两条压**存储**，这条压**比较次数**。

**IVF（倒排文件）—— 像图书馆找书**

> 先把 100 万个向量聚成 **1000 个簇**（每簇约 1000 个），记下簇中心。
> 来了 query，**先只和 1000 个簇中心比**，找出最近的比如 10 个簇。
> 再**只在这 10 个簇内部**（约 1 万个向量）精确搜索。
>
> 比较次数：1000 + 10000 = 1.1 万，而非 100 万 → **快约 90 倍**。

就像去图书馆不逐本翻，先找到"计算机类"那几个书架，再在架上找。

**HNSW（分层可导航小世界图）—— 像在社交网络里找人**

> 把所有向量连成一张**图**，相似的之间连边。检索时从入口点出发，看当前节点的邻居里谁离 query 更近就走过去，贪心重复到走不动为止。
>
> "分层"是关键：上层是稀疏的**高速公路**（少量长边，快速跨越大距离），下层是密集的**小路**（精细定位）。先在高速公路粗定位，再逐层下降精调。

现在**通常是精度/速度综合最好的方案**，且天然支持**在线插入**新向量——这对 SLAM 很重要，因为数据库随关键帧不断增长。代价是**内存开销大**（要存图结构）。

### 8.4 实际怎么组合

**FAISS**（Facebook 的库）把这些拼成工具箱。最常见的组合是 **IVF-PQ**：

```
IVF 缩小搜索范围（少比 ~90 倍） + PQ 压缩存储（小 256 倍）
```

**核心权衡是个三角**：

```
        速度
        /  \
       /    \
    内存 —— 召回率
```

ANN 是"近似"的，可能漏掉真正的最近邻。工程上调参数（如 IVF 搜几个簇、HNSW 的 `efSearch`）在三者间找平衡。

## 9. 那为什么本项目什么都没做？⭐

面试官会问。有一个**不是辩解**的好答案：

> **第一，规模不需要。** 100 张图的相似度矩阵不到 1 毫秒算完，加任何索引都是过度设计。
>
> **第二，更重要——做 baseline 评测时本来就应该用精确搜索。** ANN 是近似的，自己会引入召回损失。如果我用了 ANN，测出来的 Recall@5 就分不清是**描述子不够好**还是**索引漏检了**。用暴力精确搜索，指标干净地反映描述子质量，**这是描述子性能的上界**。
>
> 工程上正确的顺序也是这个：先把描述子质量做好并测准，规模上去了再引入 ANN，那时才能明确地说"我用 5% 的召回损失换了 100 倍速度"。

> 📌 这个回答把"我没做"变成了"**我知道什么时候该做，以及为什么现在不该做**"。是很不一样的两件事。

## 10. 面试怎么答

### Q1：你的检索是怎么实现的？

> 因为特征做了 L2 归一化，点积就等于余弦相似度，所以检索就是一次矩阵乘法：query 矩阵是 `[M,512]`，database 转置后是 `[512,N]`，相乘得到 `[M,N]` 的相似度矩阵，第 i 行就是第 i 个 query 对全部 database 的分数。然后对每一行做 `topk` 取前 K，返回的 indices 就是命中的 database 下标，拿下标去 paths 列表里查就得到文件路径。

### Q2：为什么用矩阵乘法而不是循环？

> 逻辑上等价，但性能差三个数量级——我实测过 100×100 的规模下矩阵乘法 0.39 毫秒、双层循环 46 毫秒，差 1489 倍。原因一是 Python 解释器开销，循环一万次就走一万遍解释器；二是矩阵乘法底层调的是 BLAS，会用 SIMD、缓存分块和多线程；三是在 GPU 上几千个核心可以并行。这就是向量化原则——把逐元素循环改写成整块张量运算。

### Q3 ⭐：如果数据库有一百万张图，你这套还能用吗？

> 有意思的是，计算不是第一个瓶颈。我测过 100 万张、512 维的暴力精确搜索在 CPU 上是 34 毫秒，对回环检测来说完全够——它不需要每帧都做。**先撞墙的是内存**：512 维 float32 是每张 2 KB，100 万张就是 1.9 GB，一亿张 190 GB，而机器人是嵌入式平台。
>
> 所以优化顺序是先解决存储。三条路：PCA 降维到 128 维，4 倍压缩而且配 whitening 通常还涨点；PQ 乘积量化，把 512 维切 8 段每段量化成 1 字节，压缩 256 倍，一亿张能塞进 1 GB；再就是 ANN，用 IVF 先聚成 1000 个簇只搜最近的几个簇，或者用 HNSW 的分层图做贪心搜索。实际常用 FAISS 的 IVF-PQ 组合。核心是速度、内存、召回率三者的权衡。

### Q4：那你为什么没用 FAISS？

（见 §9，两点：规模不需要 + baseline 必须精确搜索才能干净归因）

### Q5：HNSW 和 IVF 怎么选？

> IVF 靠聚类做粗筛，内存开销小、原理简单，但需要先在数据上训练聚类中心，对**增量插入**不友好——新数据分布变了簇中心就不准了。HNSW 是图结构，精度和速度综合通常更好，而且天然支持在线插入。对 SLAM 这种数据库随关键帧不断增长的场景，HNSW 更合适；代价是要额外存图结构，内存开销大。
