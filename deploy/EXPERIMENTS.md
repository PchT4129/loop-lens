# 实验记录

DINOv2 VPR 前端的推理剖析与部署优化。所有数字均为本机实测，按时间追加。

**记录规范**：每条实验含 `配置 | 预期 | 实测 | 差异解释 | 运行条件`。
预期值必须在看到实测值**之前**写下，否则这一栏没有意义。
运行条件至少包含：精度、batch、分辨率、SM 频率、功耗、是否插电、当时可用显存。

**指标口径**（复用仓库既有协议，不另造指标）：
- `deployed/*` —— 在 validation 段拟合、冻结后应用于 disjoint test 段的门控结果。
  **这是主指标**，也是唯一能当作可部署结论引用的数字。
- `oracle/*` —— 在被报告的那一段上扫阈值，只描述分数可分性。
  本项目用它辅助观察"量化是否破坏了分数分布"，不作为收益凭据。
- 特征级指标 —— 与 FP32 参考特征的余弦相似度、top-1 翻转数。
  测试集只有 30–50 query，R@1 的粒度太粗，这两个量灵敏得多。

日期：2026-09-26

### 环境基线

| 项 | 值 |
| --- | --- |
| GPU | RTX 5070 Ti Laptop，sm_120（Blackwell），46 SM，11.91 GB GDDR7 |
| 驱动 | 616.92（CUDA UMD 13.4） |
| 平台 | Windows + WSL2，23.5 GB 可见内存 / 24 核（`.wslconfig`: memory=24GB, swap=8GB） |
| Python | 3.11.15（conda env `vpr-deploy`，由 `vpr-loop-closure` 克隆而来） |
| PyTorch | 2.11.0+cu128，`arch_list` 含 `sm_120` → Blackwell 原生支持，无需 PTX JIT |
| ONNX | onnx 1.23.0 / onnxscript 0.7.2 |
| TensorRT | tensorrt-cu12 10.16.1.11 |
| 未安装 | onnxruntime-gpu、nvidia-modelopt、nsys、ncu（计划已按缺失设计降级路径） |

**env 用克隆而非重装**：省掉约 3–4 GB 的 torch 重复下载，且保证与项目基线
`vpr-loop-closure` 严格同版本 —— 延迟数字可比的前提是模型侧完全一致。

**TensorRT 选版理由**：`cu12` 而非 `cu13`，与 torch 的 cu128 同一条 CUDA 12.x 运行时，
避免同进程内两个 CUDA runtime 冲突；`10.16`（10.x 最新）而非 `11.3`，sm_120 自 10.8
起即支持，10.16 功能覆盖足够而文档与社区案例远多于 11.x。

### ⚠️ 发现 1：WSL2 下超额显存申请会静默溢出，且靠控制面板设置关不掉

**原始预期**：申请超过可用显存的一整块，应当抛 `OutOfMemoryError`。
若不抛，说明 Windows 驱动的「CUDA 系统内存回退」在生效，需要在控制面板关掉。

**实测**：申请 13.46 GB（当时可用 10.77 GB）**成功了**，没有任何报错。
于是改用写入带宽来判定它到底落在哪里：

| 分配大小 | 写入带宽 | 中位耗时 |
| ---: | ---: | ---: |
| 2.00 GB（舒适容量） | 465.3 GB/s | 4.62 ms |
| 9.15 GB（0.85 × 可用） | 508.4 GB/s | 19.33 ms |
| **13.46 GB（1.25 × 可用）** | **35.1 GB/s** | 411.66 ms |

**解释**：带宽塌了 14 倍,落在 PCIe 量级 —— 超出的部分确实被放到了系统内存。
但这**不是控制面板没设置对**：WSL2 上的 CUDA 走 WDDM 显存分页，驱动允许超订并
自行分页，而控制面板那个开关主要约束原生 Windows 应用。也就是说，这条防线在
WSL2 里守不住。

**对项目的影响**（这是本条的真正结论）：防护必须从「关掉开关」移到「按次记账」。
每个测量点都要记录峰值显存与当时可用显存，任何接近或超过物理容量的配置
一律标记为不可信，而不是直接采信它报出的延迟。本轮扫描里 ViT-B × 大 batch ×
448 分辨率最可能触发，届时必须标注而非静默采用。

自检脚本 `deploy/env/check_env.py` 已据此改写：不再用"是否 OOM"做二元判定，
而是比较"装得下"与"超额"两种情况下的写入带宽，塌陷 ≥3 倍即告警。

### 顺带得到的带宽预览

装得下时写入带宽 465–508 GB/s，对规格标称 672 GB/s 约为 **69–76%**。
这只是 `fill_` 的纯写入，不是正式的带宽测量（阶段 1 会用读写混合的微基准
重新测，并作为 roofline 的可达带宽上界）。但它已经说明：拿 672 当 roofline
的屋顶会系统性地高估上界，让每个算子都显得"效率很低"。

### ⚠️ 发现 2：空闲频率会让带宽测量偏低 12%，必须先把 GPU "叫醒"

同一个写入带宽探针在两次自检里给出了不同结果：

| 轮次 | SM 频率 | 显存频率 | 基准写入带宽 |
| --- | ---: | ---: | ---: |
| 第一次 | 1687 MHz | **14001 MHz** | 465–508 GB/s |
| 第二次 | 1515 MHz | **9001 MHz** | **426 GB/s** |

显存频率掉到 9001 MHz —— GPU 处在空闲低功耗档。带宽随之低了约 12–16%。

**对阶段 1 的影响**：测量前必须先用一段持续负载把 GPU 从低功耗档拉起来，
并在采样窗口内确认显存频率已到 14001 MHz，否则测出的"可达带宽"是空闲态的，
作为 roofline 屋顶会偏低——那会让算子显得比实际更接近上界，诊断再次失真。

这也解释了为什么"预热"不只是为了避开首次 kernel 编译：**它同时是在把硬件
拉到稳定的高频状态**。阶段 2 的计时器会把预热次数与预热后的频率一起记录。

| 量 | 实测 | 对标称 |

### ⚠️ 发现 3：显存频率会自行掉档 33–36%，且与温度、功耗墙都无关

第一次跑带宽扫描（按尺寸升序）得到"越大越慢"：256 MB 以下约 557 GB/s，
1024 MB 以上掉到约 330 GB/s。

**这个结论是假的。** 尺寸递增与时间递增完全重合，无法区分"大尺寸慢"和
"后测的慢"。于是改成**双遍 A/B/A**（第二遍倒序）并打开频率采样：

| 配置 | 第1遍(升序) | 第2遍(倒序) | 差异 |
| --- | ---: | ---: | ---: |
| triad@64MB | 573.5 | 364.6 | 36.4% |
| triad@256MB | 570.4 | 372.5 | 34.7% |
| triad@1024MB | 403.1 | 366.8 | 9.0% |
| copy@512MB | 578.4 | 377.0 | 34.8% |

**小尺寸在倒序里也慢了 36%** —— 所以变量从来不是工作集大小。
频率采样给出真正的变量：

| 显存频率 | 带宽区间 | 样本数 | 均值 |
| ---: | --- | ---: | ---: |
| 11001 MHz | 458–479 GB/s | 8 | 469 |
| 12501 MHz | 461–550 GB/s | 2 | 506 |
| 14001 MHz | 457–588 GB/s | 14 | 559 |

比例校验：`11001/14001 = 0.786`，`469/559 = 0.839` —— 带宽与显存频率近似成正比。

**排除了两个常见解释**：温度仅 57–62°C（远未到热降频阈值），
功耗 96–136 W（上限 140 W，未触墙）。掉档原因无法从 WSL2 内部确定，
但成因不影响应对方式。

**应对**：
1. `TimingResult.mem_clock_ok` 判定每个测量是否在满频下取得
2. roofline 的屋檐**只从满频样本取**（24 个带宽样本里仅 12 个合格）
3. 满频 triad 中位 494 GB/s、降频中位 366 GB/s —— 两者不可混用

**对后续阶段的影响**：ViT 的访存受限算子延迟会随这个频率波动，
所以阶段 2/3 的每个测量点都必须带频率记录，跨配置比较前先确认频率一致。

### 算力两遍高度一致，与带宽形成对照

| 配置 | 第1遍 | 第2遍 | 差异 |
| --- | ---: | ---: | ---: |
| fp32@8192 | 17.47 | 17.57 | 0.6% |
| tf32@12288 | 27.65 | 27.91 | 0.9% |
| fp16@12288 | 49.59 | 49.86 | 0.5% |
| bf16@12288 | 56.55 | 55.68 | 1.5% |
| **fp32@4096（会话首个配置）** | **11.21** | 17.22 | **34.9%** |

算力受限于功耗（131–149 W，顶到 140 W 上限）而非显存频率，所以稳定。
唯一的离群是**会话里第一个被测的配置**（fp32@4096 首遍 11.21 vs 次遍 17.22）——
即使已有预热，首个配置仍不可靠。**纪律：每个会话的第一个测量点作废不计。**

### 两个值得记住的观察

**BF16 比 FP16 快 9.5%**（59.75 vs 54.54 TFLOP/s），且两遍都一致。
在这块卡上 BF16 没有速度代价，反而更快——它的动态范围还更宽（指数 8 位 vs 5 位）。
阶段 2 的半精度基线应以 BF16 为主、FP16 作对照，而不是反过来。

**工作集大小在 64 MB–1536 MB 区间内对带宽无影响**（第 1 遍全程平坦）。
说明这个区间已全部超出 L2 缓存，测到的是纯显存带宽。

### ⭐ roofline 提前修正了阶段 3 的假设

计划里我写的假设是"batch 1 时 ViT-S 落在脊点左侧、访存受限，所以降精度无用"。
拿到脊点后可以先算一下再说。ViT-S/14 在 224px、batch 1 下，qkv 投影这个
最大的 GEMM 是 `[257, 384] × [384, 1152]`：

```
FLOPs = 2 × 257 × 384 × 1152                    = 227.4 MFLOP
Bytes = (257×384 + 384×1152 + 257×1152) × 4     =   3.35 MB      (FP32)
AI    = 227.4e6 / 3.35e6                        =  67.9 FLOP/byte
```

FP32 脊点是 30.6，**67.9 > 30.6 → 这个 GEMM 是算力受限的**，即使 batch 1。
换到 FP16 字节数减半、AI 翻倍到 135.8，而脊点 95.1 —— 仍在算力受限侧。

所以原假设**过于笼统，必须拆成两个可分别验证的命题**：

- (a) GEMM 本身访存受限 —— **已被推算否证**，它们在脊点右侧
- (b) 端到端延迟被"很多小 kernel 的启动开销 + 夹在 GEMM 之间的访存受限算子
  （LayerNorm / GELU / softmax / pos_embed 的 bicubic 插值）"主导 —— **仍待验证**

命题 (b) 才是 `torch.compile(reduce-overhead)` 的 CUDA Graph 与算子融合可能
带来收益的理由，而这与 (a) 无关。阶段 3 要用 profiler 分别量这两项：
kernel 时间总和 vs 墙钟（测启动开销占比）、以及各算子的时间占比。

## 阶段 2 — PyTorch 基线与精度参考

日期：2026-09-27

### ✏️ 更正：pos_embed 插值没有开 antialias

规划与阶段 0 里写过"每次前向跑带 antialias 的 bicubic 插值，ONNX 基本导不出去"。
**实测不对**：hub 上的 `dinov2_vits14` 实例是 `interpolate_antialias=False`、
`interpolate_offset=0.1`，只有 `*_reg` 变体才开 antialias。ONNX 的 Resize 支持
cubic 模式，所以这**不是硬性拦路虎**。

真实风险更微妙：offset=0.1 让传给插值的缩放系数是 `(16+0.1)/37` 而非 `16/37`，
PyTorch 用这个带偏移的系数做坐标映射。导出器必须精确复现"带偏移系数 +
half_pixel 坐标变换"的组合，否则产生小的数值偏差。

**固化为常量仍然是对的决定**，理由改为：消除数值保真风险 + 省掉每次前向的
冗余插值。导出可行性不再是理由。

### FP32 参考特征：跨环境逐位复现

用仓库**原有入口** `src.extract_features`（不经过任何新代码）在 `vpr-deploy` env
中抽取，与 `outputs/v3/dino_mean_*.pt`（`vpr-loop-closure` env 生成）逐位相同，meta 一致。

**"FP32 参考"的精确定义**：仓库默认开关下 `matmul.allow_tf32=False`、
`cudnn.allow_tf32=True`。后者影响卷积，而 DINOv2 的 patch_embed 正是 14×14 卷积。
实测把 `cudnn.allow_tf32` 在 True/False 间切换，输出**逐位相同**——该卷积在本卡上
走纯 FP32 算法。所以参考特征是**真·FP32**，没有藏着 TF32。

### ⚠️ 发现 4：显存降频对 ViT 延迟无影响——roofline 预测被独立印证

冒烟扫描里 16 个点有 12 个在显存降频（9001–11001 MHz）下测得。规律是 b1 轻负载
保持 14001，fp32 b8 这类重负载掉到 11001 → 9001——更像笔记本在核心与显存之间
分配功耗预算，而不是空闲降频（原因未确证）。

**关键问题不是"为什么降频"，而是"降频会不会影响这个模型的延迟"。**
roofline 推算显示 GEMM 是算力受限的，若如此，显存频率不应显著影响延迟。
直接测：同一配置反复跑 14 轮，每轮记录频率与中位延迟，按频率分桶。
加一个明确访存受限的对照组，验证探针本身有分辨力。

| 配置 | 14001 MHz | 9001 MHz | 变化 |
| --- | ---: | ---: | ---: |
| **copy 512MB（访存受限对照）** | 1.930 ms | 2.940 ms | **+52.3%** |
| ViT-S fp32 b8 224 | 11.984 ms | 11.893 ms | −0.8% |
| ViT-S bf16 b1 224 | 2.156 ms | 2.076 ms | −3.7% |
| ViT-S bf16 b8 224 | 3.863 ms | 3.864 ms | +0.0% |

- 对照组 +52.3%，与频率比 `14001/9001 = 1.556` 几乎严格成正比——探针有效
- ViT 三个配置变化都在 ±4% 内且方向不一致——**对显存频率不敏感**

这是对阶段 1 roofline 推算（qkv GEMM 的 AI=67.9 > FP32 脊点 30.6）的**独立实测印证**：
这个模型的时间不花在显存带宽上。

**对测量纪律的影响**：显存频率对 ViT 延迟**不是有效性判据**，只作记录。
**适用范围**：仅在 224px 直接探针验证；336/448px 的注意力矩阵更大、访存成分更重，
未直接验证，靠双遍 A/B/A 的差异间接把关（若某配置对频率敏感，两遍频率状态不同时
会表现为大差异）。

（bf16 b1 在低显存频率下反而快 3.7%，与"显存降频把功耗预算让给核心"的猜想一致，
但样本少且未采 SM 频率，不作结论。）

### 基线扫描

`python -m deploy.bench.bench_torch --sweep`　图：`deploy/results/baseline_latency.png`
数据：`deploy/results/baseline_torch.{csv,json}`（合并）、`baseline_torch_raw.json`（逐遍）

设置：ViT-S/14 × {fp32, tf32, fp16, bf16} × batch {1,2,4,8,16,32} × {224,336,448}px（72 点）
＋ ViT-B/14 × {fp32, fp16, bf16} × batch {1,8} × 224（6 点，仅作参照）。
每点预热 50、正式 300 次；双遍 A/B/A（第二遍倒序），两遍中位数取均值；会话首测丢弃。
整体转换精度（`model.to(dtype)`），`torch.inference_mode()`，只测 GPU 前向。
结果：**78 点、0 OOM**；两遍差 >5% 的 27 点（见发现 5）。

| ---: | ---: | ---: | ---: | ---: |

### ⚠️ 发现 5：小 batch 不稳定，且贴着一个与工作量无关的 ~2 ms 地板

不稳定性随延迟量级递减：

| 中位延迟 | 配置数 | 不稳定 | 两遍差中位 |
| --- | ---: | ---: | ---: |
| 0–5 ms | 26 | 16（62%） | 7.8% |
| 5–15 ms | 22 | 6（27%） | 3.6% |
| >15 ms | 30 | 5（17%） | 3.4% |

**GPU 频率不是原因**：最不稳定的 fp16 b1@224，第 1 遍 SM 2250 MHz → 2.17 ms，
第 2 遍 SM **2640** MHz → **4.56** ms——频率更高反而慢一倍。而慢的那遍 GPU 功耗
更低（67 W vs 87 W）：GPU 更闲，说明它在**等**。

**存在与工作量无关的地板**：两遍中较快那遍，小 batch 半精度都落在 2.0–2.3 ms
（fp16 b1@224 2.17、bf16 b4@224 2.26、fp16 b2@224 2.05、tf32 b1@224 2.03、
bf16 b1@336 2.23）。token 数翻 4 倍时 b1 延迟的变化：

| 精度 | 224 → 448px（token 4.0×） |
| --- | ---: |
| FP32 | 3.50 → 9.08 ms（**2.59×**） |
| TF32 | 2.03 → 6.43 ms（3.17×） |
| FP16 | 2.17 → 2.73 ms（**1.25×**） |
| BF16 | 2.47 → 2.74 ms（**1.11×**） |

半精度 b1 的工作量翻 4 倍，延迟几乎不动——**瓶颈不在 GPU 计算**。

**当前解释（待阶段 3 验证）**：小 batch 下 eager PyTorch 的延迟由 **CPU 发射 kernel
的速度**决定。ViT-S 每次前向约 150–180 个 kernel，每个都经过 Python 调度与 CUDA
launch，地板就在 ~2 ms；WSL2 下 CPU 调度本身有抖动，于是同一配置两遍能差一倍。
这正是阶段 1 拆出的命题 (b)。**目前是强间接证据，不是直接测量。**

### GPU 受限区：精度加速比与 roofline 屋顶比吻合

batch 32 时各精度的加速比（相对 FP32）：

| 分辨率 | TF32 | FP16 | BF16 |
| --- | ---: | ---: | ---: |
| 224px | **1.58×** | **3.32×** | 3.28× |
| 336px | 1.51× | 3.81× | 3.78× |
| 448px | 1.45× | 3.74× | 3.74× |
| 阶段 1 roofline 屋顶比 | 1.60× | 3.10× | 3.40× |

224px 下 TF32 1.58× 与屋顶比 1.60× 几乎相等，FP16 3.32× 与 3.10× 接近——
**模型在 GPU 受限区的行为与阶段 1 的矩阵乘微基准一致**。

两个随分辨率变化的趋势值得注意：**FP16 加速比随分辨率上升**（3.32 → 3.74×，
超过 GEMM 屋顶比），**TF32 加速比随分辨率下降**（1.58 → 1.45×）。
一个一致的解释：注意力的计算量随 token 数平方增长、占比随分辨率上升；
FlashAttention 只支持半精度，FP32/TF32 下的 SDPA 走别的后端。于是半精度额外吃到
注意力加速，TF32 则只加速矩阵乘、被越来越大的注意力部分稀释。**待阶段 3 用 kernel
名确认 SDPA 后端后才能下结论。**

### 测量前补充的预测 P6：小 batch 不稳定来自 CPU 大小核调度

背景：`lscpu` 显示本机 CPU 为 Intel Core Ultra 9 275HX，**8 个性能核 + 16 个能效核**。
Python 发射 kernel 是单线程的；若该线程在大小核之间被挪动，发射速度就忽快忽慢，
可以解释发现 5 里"同一配置两遍差一倍"。

**可测性的限制**：WSL2 只暴露 24 个无差别的虚拟 CPU（无频率、无核心类型信息），
虚拟 CPU 到物理核的映射由 Windows 的虚拟化层动态决定。所以**无法直接指定"跑在大核上"**，
只能间接检验：

| 子预测 | 若成立 | 若不成立 |
| --- | --- | --- |
| P6a 把进程绑定到单个虚拟 CPU 后，bf16 b1@224 多轮延迟**仍然呈双峰**（一簇 ~2.2 ms、一簇 ~4 ms 以上） | 抖动来自客户机之外（宿主把虚拟 CPU 调度到不同物理核）——与大小核假设一致，但不能证明 | 绑核后抖动消失 → 抖动来自客户机内部的线程迁移，与大小核无关 |
| P6b 不同虚拟 CPU 之间 b1 延迟**有系统性差异**（部分稳定快、部分稳定慢） | 宿主对某些虚拟 CPU 的映射相对固定，大小核假设得到支持 | 各虚拟 CPU 无差异 → 映射是浮动的，本环境下无法分离大小核效应 |

预期：P6a 大概率成立、P6b 大概率不成立——即只能得到"与大小核假设一致"的弱结论。
**这条若无法确证，如实记为"本环境下不可检验"，不强行下结论。**

### 方法：两处我自己引入的测量错误

1. **record_function 标注被当成 kernel**：第一版给每次前向打了 `forward_i` 标签，profiler 会在
   GPU 时间线上**镜像**这个标签（跨越整次前向），我的过滤条件把它计入了 kernel 时间，
   得出"GPU 忙碌 229%"。物理上不可能的数 → 先怀疑工具。修正后排除用户标注。
2. **时间线截取窗口错误**：按"本次 CPU 前向开始到下次开始"截 GPU kernel，GPU 受限时 GPU
   落后于 CPU，后半段被截掉（b8 只剩 136/156 个）。改为按 GPU 侧标注的跨度截取。

另有一个固有偏差：**profiler 会拖慢 CPU 侧**（观察者效应）。所以 GPU 忙碌占比用两种方式估计，
各自在一种区间里准确：
- 忙碌① = kernel 时间（profiler，GPU 硬件时间戳）/ **无 profiler 的墙钟** —— 发射受限时准
- 忙碌② = kernel 时间 / **同一次运行内的 GPU 跨度** —— GPU 受限且顶功耗墙时准
  （跨两次运行比较会被频率状态差异污染，第一版 fp32 b8@448 因此算出 119%）

### P2 的细节：batch 1 反而多发 23 个 kernel

| kernel | b1 | b32 |
| --- | ---: | ---: |
| `flash_fwd_kernel` | 0 | 12 |
| `flash_fwd_splitkv_kernel` + `…_combine_kernel` | 12 + 12 | 0 |
| `splitKreduce_kernel`（GEMM 的 split-K 归约） | 12 | 0 |
| 合计 | **177** | **154** |

batch 1 时工作量填不满 46 个 SM，FlashAttention 改用 split-KV、cuBLAS 对某个 GEMM 用 split-K——
把一份工作拆给更多 SM 并行，再用额外 kernel 合并结果。这是用更多 kernel 换 SM 占用率，
**但它恰好发生在已经发射受限的区间，让地板更高**。CUDA Graph 会一并消掉这部分发射代价。

### P3/P5 的细节：kernel 名揭示的几件事

- BF16 的 4 个 Linear 层被 cuBLAS/CUTLASS 分配了**4 种不同切块**的 GEMM kernel
  （`128x64`、`64x256`、`256x128`、`64x64`）——按矩阵形状选 tactic 的实例
- FP32 GEMM 为 `magma_sgemmEx_kernel`（CUDA core，名中无 `tensorop`）；BF16 为
  `cutlass_80_tensorop_bf16_s16816gemm…`（Tensor Core）
- 名字里的 `sm80` / `cutlass_80` 表示这些是按 Ampere（sm_80）一代设计的 kernel 模板，在 sm_120 上运行。
  这**不等于低效**（消费级 Blackwell 的 Tensor Core 指令与这一代同类），但值得在阶段 4 看 TensorRT 是否选了不同的 kernel
- **BF16 模式下 patch 切分卷积没有走 BF16 kernel**：b1 为 `implicit_convolve_sgemm`（FP32），b8 为
  `…fprop_implicit_gemm…tf32f32…` 并伴随两次 `nchwToNhwcKernel` 布局转换，b8 时占 GPU 时间约 5–6%
- 注意力占比随分辨率上升：b8 FP32 从 224 的 19% → 448 的 **38%**；BF16 13% → 26%。
  这支持阶段 2 的解释（半精度额外吃到 FlashAttention 加速，所以 FP16 加速比随分辨率上升）

### ❌ P4 被推翻：插值慢在 GPU 上，根因是内存布局

原始实现里 pos_embed 插值这一段：2.8（FP32）/ 4.7（BF16）个 kernel
（`upsample_bicubic2d_out_frame`、`CatArrayBatchedCopy`、类型转换与填充），CPU 约 150 µs，
**GPU 执行约 720 µs**。一个把 37×37 缩到 16×16 的插值，接近 BF16 b1 下整个 12 层网络的 GPU 工作（0.85 ms）——
**在原始模型的 BF16 b1 前向里，它约占全部 GPU 工作的 46%**。

同样 384 通道、37→16 的插值，单独测只要 92 µs。逐个变量拆开：

| 输入布局 | 尺寸参数 | 耗时 |
| --- | --- | ---: |
| **不连续视图**（DINOv2 实际写法：`reshape(1,M,M,D).permute(0,3,1,2)`） | scale_factor（带偏移） | **722 µs** |
| 不连续视图 | size=16 | 721 µs |
| 连续 NCHW | scale_factor（带偏移） | **92 µs** |
| 连续 NCHW | size=16 | 92 µs |

**只改内存布局差 7.9 倍**，缩放参数写法无影响（1.00×），两种布局输出逐位相同。
722 µs 与模型内测到的 ~720 µs 吻合。不连续视图的步长是 `(525696, 1, 14208, 384)`——
相邻像素在内存里相隔 384 个数。

**机制（与数据一致，未读 kernel 源码确认）**：相邻线程处理相邻输出像素，读取相邻输入像素；
连续布局下这些地址挨在一起，硬件可合并为少量内存事务；不连续视图下相邻像素相隔 1536 字节，
每个线程的读取落在不同的缓存行，无法合并。

附带的微基准：固定输出 16×16 时耗时与通道数近似成正比（48→768 通道：18→178 µs）。

**这回头完整解释了阶段 2 对照实验 1**：固化常量省下的 0.73 ms（fp32 b1、bf16 b8）正是这个 kernel 的
~720 µs GPU 时间；bf16 b1 处于发射受限区、GPU 有大量空闲，删掉一段 GPU 工作省不下多少墙钟，
所以那一格不显著（+0.18 ms，IQR 跨 0）——**与"GPU 侧开销"的解释完全自洽**，而与我原先"CPU 侧开销"
的猜测矛盾。

**若分辨率必须动态**（无法固化常量），一行 `.contiguous()` 就能把这段从 722 µs 降到 92 µs。

### ⚪ P6：慢状态真实存在，但诱因未能识别

阶段 2 的"同一配置两遍差一倍"在今天的多次实验中**间歇出现**：

| 运行 | bf16 b1 无 profiler 墙钟 | GPU kernel 时间 |
| --- | ---: | ---: |
| 剖析第 3 次（快状态） | 2.52 ms | 0.837 ms |
| 剖析第 4 次（慢状态） | **4.45 ms** | **0.826 ms** |

**GPU kernel 时间在两种状态下一致，只有墙钟变了 ~1.75 倍——慢状态确定在 CPU 侧。** 这是直接证据。

为找诱因，主动操纵了三个变量（每次都在测"不操纵"的对照组）：

| 假设 | 操纵 | 结果 |
| --- | --- | --- |
| 客户机内线程迁移 | 绑定到单个虚拟 CPU（8 个不同 vCPU，12 轮） | 对照组本身就不抖（全在 2.0–2.2 ms），**无法检验** |
| 平台功耗在 CPU/GPU 间转移 | 测前先跑 3 s 重负载（138 W）/ 空闲（19 W）/ 轻负载 | 三者差异 ±1.5%，**否定** |
| 测量工具自身干扰 | 计时器的 nvidia-smi 条件采样开/关，10 轮配对 | 首轮三组同向 +0.6~1.1%；**复跑为 +0.3% / +1.8% / −2.8%，方向不一致 → 在噪声内**，不是原因（见文末复现记录） |

绑核实验在慢状态出现后立即重跑了一次，但慢状态已消失；该次运行内有 +14% 的缓慢漂移，
而各 vCPU 按编号顺序测，**漂移与 vCPU 编号混杂**，vCPU 16/20/23 看似稍慢不能归因于核心本身。

**决定停止追查。** 三个可操纵的诱因均已排除，剩余可能在 Windows 侧（后台活动等），从 WSL2 内部
无法观测，继续投入会让前置阶段膨胀。

**对主线的影响**：
- ~2 ms 地板本身稳定可复现（今天所有快状态实验都在 2.0–2.2 ms）——这是阶段 4 的 batch 1 基线
- 瞬时 CPU 侧变慢会发生且无法预先排除 → **阶段 4 的 batch 1 对比一律用配对交替多轮**，让偶发变慢
  同时落在两个对照臂上；报告逐轮分布而非单个数
- 阶段 2 表中"两遍均值"类的 b1 数（如 fp16 b1 的 3.37 ms）混合了两种状态，**不引用**

### R1 结果：协议层面完全相同，特征层面 BF16 差 FP16 约 60 倍

特征级（`compare_features`，数据 `deploy/results/compare_r1.json`）与协议级（冻结 FP32 gate，
日志 `deploy/results/protocol/r1_*/`）：

| 变体 | 1−余弦 均值 | 余弦 最小 | top-1 翻转 | 门控决策翻转 | oracle R@100%P | 留出 R@1 | deployed F1 [95% CI] | FP |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- | ---: |
| FP32 @ batch 1 | ~0（分数漂移 1.1e-7） | 1.000000 | 0/200 | 0/50 | 0.2326 | 0.9333 | 0.8478 [0.7473, 0.9263] | 7 |

| **BF16**（整体转换） | **1.8e-4** | 0.999492 | **15/200** | 0/50 | 0.2093 | 0.9333 | 0.8478 [0.7473, 0.9263] | 7 |
| BF16（autocast） | 1.4e-4 | 0.999694 | 3/200 | 0/50 | 0.2326 | 0.9333 | 0.8478 [0.7473, 0.9263] | 7 |

**对照预期**：
- FP32 @ batch 1：✅ 与 batch 16 的参考无可分辨差异（分数漂移 1.1e-7，接近余弦噪声底）
- FP16 / BF16：✅ 余弦 >0.999、deployed F1 落在 CI 内——实际是**逐位相同**
- autocast 比整体转换 BF16 更接近 FP32：✅ 但余弦只好 22%，top-1 翻转 15 → 3 更明显

**BF16 的特征误差是 FP16 的 62 倍，与位数理论吻合**：BF16 尾数 7 位、FP16 尾数 10 位，单次舍入的
相对误差差 2³ = 8 倍；小误差时 `1 − cos ≈ ‖δ‖²/2`，与误差的平方成正比 → 预测 8² = 64 倍，实测
1.8e-4 / 2.9e-6 = 62 倍。

**结论：在这个模型上 FP16 在速度（阶段 2）和精度两个轴上都优于 BF16。** BF16 的优势是动态范围，
而本模型在 FP16 下没有溢出，这个优势用不上。**后续档位以 FP16 为半精度主线**，BF16 不再跟进。
这修正了阶段 1"以 BF16 为主"的建议（阶段 2 已从速度角度修正过一次，这里从精度角度再修正一次）。

**为什么需要特征级指标**：BF16 的 15 次 top-1 翻转和 R@100%P 少掉的 2 个查询，在 R@1 与 deployed F1
上**完全不可见**——翻转发生在容差（±3 帧）内的相邻帧之间，不改变对错。只看任务指标，会误以为
三种精度毫无区别。

**决策翻转的余量——FP16 安全，BF16 靠运气**（✏️ 本段初稿写成"离阈值最近的查询距离阈值远大于分数
漂移"，对 BF16 不成立，已更正）：

| | 门控测试段上离阈值最近的查询 | 全量最大分数漂移 | 比值 |
| --- | ---: | ---: | ---: |
| FP16 | 4.41e-3 | 6.9e-4 | 漂移只有余量的 **1/6** → 翻转不可能 |
| BF16 | 4.41e-3 | **6.0e-3** | 漂移**已超过**余量 |

BF16 这次 0 次决策翻转，只是因为漂移最大的那几个查询恰好不是离阈值最近的那个——**是运气，不是余量**。
查询更多、更多分数落在阈值附近时，BF16 会出现决策翻转，FP16 不会。这进一步支持选 FP16。

R1 未另做"重新拟合 gate"的对照：冻结 gate 下 0 次决策翻转、协议输出逐位相同，重拟合不会提供新信息。

### R2 测量前的预期（因 R1 结论，主角由 BF16 改为 FP16）

阶段 3 实测 FP16 b1 的 GPU kernel 时间 0.89 ms、eager 墙钟 2.0–2.5 ms。

| 变体 | 预期 | 理由 |
| --- | --- | --- |
| compile `reduce-overhead` FP16 b1 | **0.85–1.05 ms**（eager 的 **2–2.5×**） | CUDA Graph 消掉发射开销，墙钟逼近 GPU 工作量 |
| compile `default` FP16 b1 | **1.3–1.8 ms** | 只有融合：kernel 数减少，发射开销按比例下降，但仍逐个发射 |
| compile `max-autotune` FP16 b1 | 与 reduce-overhead 接近或略快 | max-autotune 同样使用 CUDA Graph，外加更多 GEMM 候选 |
| compile `reduce-overhead` FP32 b1 | 3.37 → **~3.0 ms**（≤1.2×） | FP32 b1 本已 ~90% GPU 受限 |
| compile 任意模式 FP16 b32 | 比 eager 快 **≤10–15%** | GPU 受限，只有融合起作用 |
| compile 的数值 | 与同精度 eager 余弦 ≥ 1−1e-5 | 融合改变求和顺序，但精度不变 |

**测量前对 R2 预期的一处修正**：冒烟时 Inductor 警告 `Not enough SMs to use max_autotune_gemm mode`。
源码（`torch/_inductor/utils.py`）的门槛是 `min_sms = 68  # 3080`，而本卡只有 46 个 SM。所以在这块卡上
`max-autotune` **不会为矩阵乘生成和筛选候选 kernel**，GEMM 照旧走 cuBLAS。原预期"max-autotune 外加更多
GEMM 候选"不成立 → 修正为：**max-autotune ≈ reduce-overhead**（两者都用 CUDA Graph，GEMM 实现相同）。

冒烟结果：`default` 与 `reduce-overhead` 均以 `fullgraph=True` 一次捕获成功，**无图断点**。

| FP16 编译后延迟 | 第 1 次 | 第 2 次 | 差异 |
| --- | ---: | ---: | ---: |
| `reduce-overhead` b1 | 0.889 ms | 0.863 ms | 3% |
| `max-autotune` b1 | 0.889 ms | 0.829 ms | 7% |
| `default` b1 | 1.818 ms | 1.465 ms | **19%** |
| `max-autotune` 相对 `reduce-overhead` @ b32 | 快 7% | **慢 1%** | ❌ 未复现 |

**✏️ 更正**：第 1 次运行后我写了"b32 上 max-autotune 快约 7%（选了融合偏置的 cuBLAS 调用）"。第 2 次两者在
波动范围内一致（11.14 vs 11.00 ms），**该结论未复现，撤回**。autotune 日志里 `bias_addmm` 单个 GEMM 更快是
真实的，但对整个前向的影响落在运行间波动内，无法分辨。

**⭐ 一个预期之外的发现：CUDA Graph 让延迟变稳定了**。带 CUDA Graph 的两种模式两次运行只差 3–7%，
只做融合的 `default` 差了 19%。`default` 仍需 CPU 逐个发射 kernel，于是继承了阶段 3 发现的 CPU 侧间歇性抖动；
CUDA Graph 把 CPU 从关键路径上拿掉，延迟就只由 GPU 决定。**对机器人而言，"更稳"与"更快"同样重要**
（p99 决定实时保证）。这一点可在阶段 4b 用 p99/中位数比值直接检验。

**对照预期**：
- `reduce-overhead` FP16 b1：两次 0.889 / 0.863 ms，✅ 落在 0.85–1.05 ms；与阶段 3 的 GPU kernel 时间（0.891 ms）
  一致——**发射开销消除后，墙钟 = GPU 工作量**，这一结论两次都成立
- `reduce-overhead` FP32 b1：2.909 ms（1.18×），✅ 落在 ~3.0 ms、≤1.2× 的预期
- FP32 b32 任何模式：1.00–1.03×，✅ GPU 受限时编译几乎无益
- FP16 b32：1.09–1.17×，✅ 融合带来 ≤10–15% 的收益（两次都在区间上沿附近）
- **编译耗时**：`default`/`reduce-overhead` 3–5 s，`max-autotune` 15–22 s（冷启动缓存）；在这块卡上多花的
  时间换不来可分辨的延迟收益（SM 门槛使 GEMM 不参与调优）

### ⚠️ R2 显存数据无效——我重犯了阶段 2 的"同时驻留"错误

`bench_compile.py` 的显存阶段测出 FP16 eager 峰值 allocated **139 MB**，而阶段 2 单独驻留时是 **53 MB**。
原因：`main()` 里 FP32 基座模型（82.5 MB）一直留在显存上，被计入每个变体的峰值（139 ≈ 82.5 + 41 + 激活）；
前面延迟测量留下的 CUDA Graph 内存池也可能未释放干净。**这组显存数不引用。**

修正方案：`deploy/bench/memory_isolated.py`，**每个变体在独立子进程里测**（新进程没有任何残留）。
顺带测 PyTorch 看不到的 **CUDA context** 与进程总占用——那才是它从机器人共享显存预算里实际拿走的量。

### R2 显存（独立进程，batch 1）

`python -m deploy.bench.memory_isolated`（数据 `deploy/results/memory_isolated_r2.json`）

**测量方法上又踩了一个坑**：第一版用 `nvidia-smi` 读"子进程启动前整卡已用"，用 `torch.cuda.mem_get_info`
读"子进程稳态已用"，得出进程占用 **−3.9 GB**。WSL2 下两个接口对"已用"的口径本来就差约 4 GB
（阶段 0 即可见：nvidia-smi 报 4.9 GB，CUDA 报 1.1 GB），不能相减。改为两端都用 `mem_get_info`，
并加有效性自检（进程总占用必须 ≥ reserved）——全部通过。

| 变体 | 权重 | peak allocated | peak reserved | 进程总占用 | 相对 FP16 eager |
| --- | ---: | ---: | ---: | ---: | ---: |
| FP16 eager | 41.1 MB | 53.6 MB | 60 MB | **108 MB** | — |
| FP16 `default` | 41.1 | 53.7 | 60 | 108 | +0 |
| FP16 `reduce-overhead` | 41.1 | 53.7 | 82 | **142** | **+34 MB（+31%）** |
| FP16 `max-autotune` | 41.1 | 88.3 | 118 | 178 | +70 MB（+65%） |
| FP32 eager | 82.1 | 96.3 | 114 | 162 | +54 MB |
| FP32 `reduce-overhead` | 82.1 | 94.8 | 116 | 176 | +68 MB |

- FP16 eager 53.6 / 60 MB 与阶段 2 单独驻留测得的 53 / 60 MB 一致 —— 隔离有效
- **CUDA Graph 的显存代价**：`reduce-overhead` 的 reserved +22 MB、进程总占用 +34 MB——它为录制的图
  预留的专用内存池
- `max-autotune` 多出 35 MB allocated，是自动调优与更大的图内存池的代价
- "CUDA context"一列测得 ≈0：CUDA 默认**懒加载** kernel 代码，建立 context 时几乎不占显存，

  从 Windows 整机角度的真实占用无法在 WSL2 内完全核实。**同一口径下的相对比较是可靠的。**

### R2 精度：编译不改变特征，甚至略微更接近 FP32

`compare_features`（数据 `deploy/results/compare_r2.json`）与协议（`deploy/results/protocol/r2_*`）：

| FP16 | 相对 FP32：1−余弦 | top-1 翻转 | 分数漂移 均 | 决策翻转 | oracle R@100%P | deployed F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |

| compile `default` | **2.6e-6** | **1/200** | **1.1e-4** | 0/50 | — | — |

- **预期 ✅**：编译版相对同精度 eager 的 1−余弦 = 1.1e-6，满足 ≥ 1−1e-5
- `default` 与 `reduce-overhead` 的特征**逐位相同**——CUDA Graph 只改变"怎么发射"，不改变数值
- **编译后的 FP16 比 eager FP16 更接近 FP32**（分数漂移减半、R@100%P 回到 FP32 的值）。与融合的机制一致：

- 编译耗时：这次抽特征时 `reduce-overhead` 首次调用 1.48 s、`default` 0.65 s，远低于基准测试中的 3.5–5 s——

| --- | ---: | ---: | --- | --- |
| R0 FP32 eager | 3.4 ms | 162 MB | 参考 | — |
| R1 FP16 eager | 2.2–2.4 ms | 108 MB | 1−cos 2.9e-6，F1 不变 | 显存 −33%，但 b1 延迟只快 ~1.5×（发射受限） |

而不是低精度本身**——这正是阶段 3 诊断所预测的。

下一档（4b）的问题因此变得很具体：TensorRT 在 GPU 侧能否把 **0.86 ms 的 GPU 工作量**本身再压缩
（更好的 GEMM kernel、融合的注意力）；以及它不依赖 Python 运行时，进程显存能否低于 PyTorch 的 108–142 MB。

## 阶段 4b — ONNX 导出（R3）与 TensorRT FP16（R4）

日期：2026-09-28

**范围说明**：计划中 R3 的 ONNX Runtime 延迟档因 `onnxruntime-gpu` 未安装而跳过（阶段 0 已约定的降级路径）。
改用 **TensorRT FP32 引擎**核对导出图的数值正确性：它与 PyTorch FP32 的差异，就是"导出 + TRT 执行"
本身引入的差异，与低精度无关。

### 测量前的预期

依据：4a 测得 FP16 b1 的 GPU 工作量 ≈ 0.86–0.89 ms，compile `reduce-overhead` 已把延迟压到这个值；
PyTorch 每次前向 154–178 个 kernel。

| 项 | 预期 | 理由 |
| --- | --- | --- |
| ONNX 导出 | 一次成功，无需改模型 | 4a 中 Dynamo 已无图断点捕获整个模型；pos_embed 已固化为常量 |
| TRT FP32 引擎 vs PyTorch FP32 | 1−余弦 ≤ 1e-6，0 次翻转 | 同精度，只有 kernel/求和顺序差异（TF32 需显式关闭） |
| TRT FP16 kernel 数 / 前向 | **明显少于 154**（约 40–90） | 层融合：LayerNorm、GELU、残差加并入相邻层；注意力融合为少数 kernel |
| TRT FP16 b1 延迟 | **0.55–0.80 ms**（比 compile 的 0.86 ms 快 10–35%） | 发射开销已无关紧要（C++ 发射、kernel 更少），剩下的只能靠 GPU 工作量本身变少 |
| TRT FP16 b32 延迟 | 比 compile `reduce-overhead`（~11.0 ms）快 **5–15%** | 按实际形状试跑挑 tactic + 更深的融合 |
| TRT FP16 精度 | 1−余弦 ≤ 1e-5，0 次决策翻转，deployed F1 不变 | TRT 默认让归一化等敏感层以 FP32 累加 |
| 引擎构建耗时 | 30 s – 5 min | 为每层试跑候选 tactic |
| 进程显存 | 与 PyTorch FP16 eager 同量级（~100–200 MB），把握较低 | 权重相同（41 MB）；TRT 自身的运行时开销未知 |

### 结果

`bash deploy/run_stage4b.sh` 跑通了导出、构建、精度与协议；延迟与显存两步因测量脚本错误重跑（见下）。
数据：`onnx_export.json`、`trt_build.json`、`compare_r4.json`、`trt_r4.json`、`memory_isolated_r2.json`、
`protocol/r4_*`。

#### 导出与构建

- **ONNX**：新导出器（dynamo）一次成功，opset 20，432 个节点，83 MB，2–3 s。**注意力被拆开**
  （12 个 `Softmax`；72 个 `MatMul` = 48 个 Linear + 每层注意力 2 个）
- **引擎**：TensorRT 解析得到 1706 层（含常量） → 优化后 FP16 引擎 **92 层**、FP32 引擎 128 层；
  FP16 构建 11–12 s、FP32 5–23 s（远快于预期的 30 s–5 min）；FP16 引擎 44 MB、FP32 83 MB
- **注意力被 TensorRT 重新融合**：FP16 引擎中出现 12 个 `_gemm_mha_v2` 融合层——每个 block 一个。
  FP32 引擎中没有（`gemm` 72 层 = 注意力未融合），与"融合 MHA kernel 只有半精度版"一致
- **整个网络被 Myelin 接管**：所有层名都带 `myl0` 后缀，层类型为 `kgen`（Myelin 生成的 kernel）/

  "myl"），已修正脚本，旧 JSON 中该字段作废
- 构建警告：`F.normalize` 的 `eps=1e-12` 在 FP16 下无法表示、被截为 0。只在特征范数为 0 时有影响，
  实际不会发生；记录在案

#### 延迟（修正后）

**✏️ 第一次运行的两个测量错误**：
1. 执行器用了 PyTorch **默认 stream**，TRT 警告会为此额外调用 `cudaStreamSynchronize`——每次调用都同步，

## 阶段 4c — TensorRT INT8（R5）

日期：2026-09-30

### 范围与方法

- **量化方式：TensorRT 的隐式量化 + 训练后校准（PTQ）**。`nvidia-modelopt` 未安装（阶段 0 的约定），
  所以本轮用 TensorRT 自带的校准器：打开 `INT8` 标志（同时保留 `FP16`），给一个 `IInt8Calibrator`，
  TensorRT 用校准图像统计每个张量的激活范围、算出缩放因子，再**自行决定**哪些层跑 INT8。
  ⚠️ 隐式量化自 TensorRT 10.1 起已标注为 deprecated，官方推荐显式 Q/DQ（ModelOpt 的做法）。
  这里用它是"不装新依赖能走通的最短路径"；显式 Q/DQ 与逐层控制留给阶段 5
- **校准集**：`day_right` 000–049，50 张，经 `get_default_transform(224)`——与推理预处理逐位一致。
  与测试段（`night_right` 050–099）不同 traversal、也不重叠帧号区间；库（`day_left`）不进校准集
- **两个单变量对照**：
  - 校准算法：Entropy（KL 散度选截断阈值，TensorRT 默认推荐）vs MinMax（不截断，用最大绝对值）
  - 校准集的域：`day_right` 000–049 vs `night_right` 000–049（与门控 validation 段同源，不碰 test）
- **精度评估**：与 4a/4b 完全相同——batch 1 抽特征，`compare_features` 特征级指标，冻结 FP32 门控跑协议
- **先看 INT8 到底落在哪些层**：用引擎检查器数各层输入的数据类型。隐式量化下 TensorRT 只在"INT8 更快"时才选 INT8，
  且 Myelin 接管的融合子图未必支持隐式 INT8——**"开了 INT8 标志"不等于"跑在 INT8"**

### 测量前的预期（在看到任何 INT8 结果之前写下）

依据：TRT FP16 b1 GPU 工作量 0.53–0.58 ms、+CUDA Graph 墙钟 0.50–0.53 ms；阶段 3 GEMM 占 GPU 时间 BF16 b1 ~48%、b32 ~63%；
TRT FP16 1−cos 1.2e-5、最大分数漂移 1.5e-3、决策余量 4.41e-3。

| 项 | 预期 | 理由 |
| --- | --- | --- |

#### 机制：DINOv2 的离群通道（`deploy/diagnostics/activation_outliers.py`）

**① 观察**（FP32 模型、50 张校准图、25 个 LayerNorm 输出）：
- 我在 PyTorch 里测到的每层 max|x| 与 TensorRT MinMax 缓存的 amax **逐层相等**（如 layer_norm_1 均为 117.7）——
  名字映射与校准数据都对上了，缓存解码可信
- **离群值集中在少数固定通道**：通道 278、68、208、323、1、379 在多个层反复成为最大的通道。
  例：layer_norm_1 的通道 199 达 117.7，而中位通道的最大值只有 6.2（19 倍）；layer_norm_7 的通道 278 为 32.0，中位通道 5.5
- **Entropy 的截断点普遍低于这些离群通道**：layer_norm_7 截在 13.7（真实 max 32.0），layer_norm_1 截在 15.7（真实 117.7）

**② 操纵（单变量）**：只把 25 个 LayerNorm 输出按 TensorRT 自己的缩放因子伪量化成 INT8，其余全部 FP32：

| 只量化 LayerNorm 输出 | 1−cos | 最小 cos | top-1 翻转 | 最大分数漂移 | 决策翻转 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 用 Entropy 的缩放因子 | 3.5e-2 | 0.805 | 60/200 | 0.094 | 4/50 |
| 用 MinMax 的缩放因子 | 3.9e-3 | 0.976 | 34/200 | 0.023 | 1/50 |

- **仅此一处就复现了 Entropy 比 MinMax 差、而且差一个数量级的排序**——截掉离群通道比"分辨率变粗"更伤
- 但它只解释了整体误差的**一部分**（Entropy：3.5e-2 vs 完整 INT8 引擎的 0.26；MinMax：3.9e-3 vs 0.10）。
  剩余误差来自其他被量化的张量（注意力内部 Q/K/V 与 softmax 输出、GELU 输出等）——逐层归因留给阶段 5

### 阶段 4c 小结：拐点在 FP16 与"全模型隐式 INT8"之间

| 档 | b1 延迟 | b32 延迟 | 进程显存 | held-out R@1 | deployed F1 |
| --- | ---: | ---: | ---: | ---: | --- |
| FP32 eager | 3.4 ms | 45 ms | 162 MB | 0.933 | 0.848 [0.747, 0.926] |
| **FP16 TRT + CUDA Graph** | **0.51 ms** | 7.6–7.9 ms | 106–118 MB | **0.933** | **0.848**（逐位不变） |
| INT8 TRT（隐式，Entropy day）+ Graph | 0.47 ms | 6.9 ms | 98 MB | 0.633 | 0.667 [0.533, 0.791] |

**用 8% 的延迟和 20 MB 显存，换来 30 个点的 R@1 和翻倍的误报——这笔交易不成立。**
全模型隐式 INT8 已经越过了拐点；FP16 仍是这个模型当前的帕累托最优点。

**下一步（阶段 5 的问题因此变得很具体）**：不是"要不要 INT8"，而是**哪些层可以安全地 INT8**。
候选方向：保留 LayerNorm 输出 / 注意力内部为 FP16、只量化 Linear 的 GEMM（显式 Q/DQ 逐层控制），
或处理离群通道（逐通道缩放、SmoothQuant 式的把激活离群值"挪"到权重里）。这需要显式量化工具——
是否安装 `nvidia-modelopt` 待用户决定；不装的退路是手工往 ONNX 里插 Q/DQ 节点。

## 阶段 5 — 逐组量化敏感度（显式量化，ModelOpt）

日期：2026-09-30

### 问题

4c 的结论是"全模型隐式 INT8 越过拐点"。阶段 5 问的是：**哪些层可以安全地 INT8？**
两步：① 在 PyTorch 里用伪量化做逐组敏感度（便宜，300 张图几秒一组）；② 只把有希望的配置导出成带 Q/DQ 的 ONNX，
用 TensorRT **显式** INT8 建引擎，核对真实引擎的精度与模拟一致，并测速度。

### ModelOpt 的默认 INT8 配方到底量化了什么（先看清再设计）

`INT8_DEFAULT_CFG` 在我们的模型上插入 197 个量化器、启用 123 个：patch_embed 卷积（输入 + 权重）、
**25 个 LayerNorm 的输入**（也就是残差流本身）、48 个 Linear 的输入与权重。注意力内部的 Q·Kᵀ 与 softmax·V 不量化。
权重逐输出通道（axis 0）、激活逐张量；校准算法 `max`（即 MinMax）。
所以"默认配方"≠"只量化 Linear"，下面把这些分开测。

### 设计

- 校准：`day_right` 000–049（与 4c 相同）；精度评估与 4a–4c 相同（batch 1、`compare_features`、冻结 FP32 门控）
- 分组（每组只启用这一组的量化器，其余全部 FP32）：

| 组 | 启用的量化器 |
| --- | --- |
| `none` | 全部关闭（sanity check：必须与 FP32 逐位相同） |
| `weights` | 48 个 Linear 的权重（逐通道），激活不量化 |
| `qkv` / `proj` / `fc1` / `fc2` | 该类 Linear 的输入 + 权重（各 12 个） |
| `linear` | 全部 48 个 Linear 的输入 + 权重 |
| `ln_in` | 25 个 LayerNorm 的输入（残差流） |
| `conv` | patch_embed 卷积 |
| `default` | ModelOpt 默认配方的全部 123 个 |
| `linear+sq` | 全部 Linear，SmoothQuant 算法 |

### 测量前的预期

依据：4c 只伪量化 LayerNorm **输出**（MinMax）是 1−cos 3.9e-3；LayerNorm 输出 = qkv 与 fc1 的输入；
DINOv2 的巨大激活在残差流里更大（LayerNorm 之前）。

| 组 | 预期 1−cos | 理由 |
| --- | --- | --- |
| `weights` | 1e-5 – 1e-4 | 权重逐通道量化通常很温和 |
| `proj` | 1e-4 – 1e-3 | 注意力输出没有已知的巨大离群值 |
| `qkv` | 1e-3 – 3e-3 | 输入是 norm1 的输出，含离群通道 |
| `fc1` | 1e-3 – 3e-3 | 输入是 norm2 的输出，同上 |
| `fc2` | 1e-3 – 1e-2 | GELU 之后，文献中 ViT 的 fc2 输入离群值大 |
| `ln_in` | **1e-2 – 1e-1**（最敏感） | 残差流的巨大激活，逐张量量化必然把其余值压得很粗 |
| `linear` | 5e-3 – 1e-2 | 四类之和的量级 |
| `default` | ≥ `ln_in` | 包含 `ln_in` |
| `linear+sq` | 比 `linear` 低 3–10 倍 | SmoothQuant 把激活离群值挪到权重，权重逐通道扛得住 |

**"可接受"的判据（事先定下）**：严格——最大分数漂移 < 决策余量 4.41e-3（不可能翻转任何决策）；
宽松——held-out R@1 ≥ 0.9 且 deployed F1 的 CI 与 FP32 重叠。
**预期 `linear+sq` 能达到宽松判据，未必达到严格判据**；`linear`（不做 SmoothQuant）达不到宽松判据。

### 结果 ①：逐组敏感度（PyTorch 伪量化，`deploy/quant/sensitivity.py`，数据 `ptq_sensitivity.json`）

| 组 | 量化器 | 1−cos | 最小 cos | top-1 翻转 | 最大分数漂移 | 决策翻转 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `none`（sanity） | 0 | **0** | 1.0000 | 0/200 | 0 | 0/50 |
| `conv` | 2 | 2.7e-4 | 0.9980 | 11 | 0.0044 | 0 |
| `proj` | 24 | 4.4e-4 | 0.9986 | 12 | 0.0067 | 0 |

### 阶段 5 小结：选择性 INT8 找回了任务精度，但严格意义上的"零代价"只有 FP16

| 档 | b1 延迟 | 显存 | held-out R@1 | deployed F1 | 特征 1−cos | 最大分数漂移 / 余量 |
| --- | ---: | ---: | ---: | --- | ---: | ---: |
| FP16 TRT + CUDA Graph | 0.52 ms | 118 MB | 0.933 | 0.848 [0.747, 0.926] | 1.2e-5 | 0.34 倍 |
| **显式 INT8（qkv/proj/fc1 + SmoothQuant）+ CUDA Graph** | **0.46 ms** | **90 MB** | 0.900 | 0.882 [0.796, 0.949] | 9.0e-4 | 2.5 倍 |
| 隐式 INT8（全部）+ CUDA Graph | 0.47 ms | 98 MB | 0.633 | 0.667 [0.533, 0.791] | 0.26 | 50 倍 |

- **显式选择性 INT8 是新的帕累托点**：比 FP16 快 14%、省 24% 显存，任务指标在噪声范围内（R@1 差一个查询，F1 落在 CI 内）
- 但它**不是免费的**：特征误差比 FP16 大 75 倍，最大分数漂移是决策余量的 2.5 倍——只是这次恰好只翻转了一个决策、
  一个 top-1（查询 76，落在容差边界外 1 帧）。查询更多时它会翻转更多
- **拐点的精确位置**：FP16 是"特征级零代价"的最后一档；选择性 INT8 是"任务级在噪声内"的最后一档；
  全模型 INT8 两个层面都越过了拐点
- 对部署的建议：显存 / 功耗预算紧时用显式选择性 INT8（fc2 与注意力保留 FP16、其余 Linear 用 SmoothQuant）；
  对误报零容忍的场合用 FP16——50 个查询的测试段不足以证明 INT8 的零误报能力

（零误报召回的逐查询排查由 `deploy/diagnostics/zero_fp_breakpoint.py` 复现，数据 `diagnostics/zero_fp_breakpoint.json`。

## 阶段 6 — FP8 与 NVFP4（支线收尾）

日期：2026-09-30

### 问题与方法

INT8 的困难是**逐张量的均匀格点**装不下 DINOv2 的离群通道（阶段 4c、5）。另外两种低精度格式从不同方向绕开它：
- **FP8（E4M3）**：仍是逐张量一个缩放因子，但格点是**浮点**的——4 位指数、3 位尾数，数越小格点越密。
  离群值和普通值都能保住**相对**精度，代价是每个数只有 3 位尾数（相对误差约 ±6%）
- **NVFP4（E2M1 + 块缩放）**：每 **16 个数**一个 FP8 缩放因子（动态、按块），离群值只影响它所在的那一块；
  代价是每个数只有 1 位尾数

方法与阶段 5 相同：PyTorch 伪量化做逐组敏感度 → 选配置 → 导出建引擎核对 → 测速度与显存。
格式是唯一变量：分组、校准集（day_right 000–049）、评估流程全部不变。

### 测量前的预期

| 项 | 预期 | 理由 |
| --- | --- | --- |
| FP8 全部 Linear，1−cos | **1e-3 – 5e-3**（比 INT8 的 2.3e-2 好 5–20 倍） | 浮点格点对离群值宽容；fc2 不再一家独大 |
| FP8 全部（Linear + LN 输入 + 卷积） | 与全部 Linear 同量级 | 残差流的离群值对浮点格式影响小 |
| FP8 任务级 | 达到宽松判据；**不一定**达到严格判据 | 3 位尾数的相对误差仍会让分数漂移几个 1e-3 |
| FP8 延迟（TRT） | b1 + Graph 比 FP16 快 ×1.05–1.2；b32 快 ×1.1–1.3 | FP8 Tensor Core 理论 2× FP16，与 INT8 同档；b1 小矩阵收益打折 |
| FP8 显存 | 85–100 MB | 权重 1 字节，与 INT8 同 |
| NVFP4 全部 Linear，1−cos | 1e-2 – 5e-2 | 块缩放隔离离群值，但 1 位尾数太粗 |
| NVFP4 任务级 | **达不到**宽松判据（R@1 < 0.9 或 CI 下移） | 同上 |
| NVFP4 引擎 | **工具链风险高**：TensorRT 的 FP4 路径主要为大语言模型设计，ONNX 导出与构建可能不通 | 若不通，如实记为工具链限制，只报告 PyTorch 模拟的精度 |

### 结果 ①：逐组敏感度（伪量化，`ptq_sensitivity.json`，格式前缀 `fp8:` / `fp8pc:` / `nvfp4:`）

| 组 | INT8（阶段 5） | FP8 | NVFP4 |
| --- | ---: | ---: | ---: |
| `none`（sanity） | 0 | **0** | — |
| `weights`（只量化权重） | **5.9e-4**（逐通道） | 4.2e-3（逐张量）；3.85e-3（逐通道 `fp8pc`） | 5.5e-2 |
| `linear_in`（只量化 Linear 输入） | 2.3e-2 | **1.4e-3** | 2.1e-2 |
| `qkv` / `proj` / `fc1` | 6.8e-4 / 4.4e-4 / 3.3e-3 | 1.4e-3 / 1.1e-3 / 1.3e-3 | — |
| `fc2` | 1.6e-2 | **1.9e-3** | 2.5e-2 |
| `ln_in` | 7.4e-3 | 1.0e-3 | — |
| `linear`（全部 Linear） | 2.3e-2（+SQ 5.1e-3） | **5.7e-3**（逐通道权重 5.35e-3） | 8.2e-2 |
| 全部（卷积 + LN 输入 + Linear） | 3.5e-2 | 1.8e-2 | — |

- **FP8 与 INT8 各有所长，而且正好互补**：同样的 Linear 层，**激活**用 FP8 比 INT8 好 17 倍（1.4e-3 vs 2.3e-2）——浮点格点对离群值宽容，
  fc2 从最敏感变成和其他组差不多（1.9e-3）；**权重**用 INT8（逐通道）比 FP8 好 7 倍（5.9e-4 vs 4.2e-3）——权重分布接近钟形、没有巨大离群值，
  均匀的 255 个格点比 3 位尾数的浮点更准
- FP8 权重逐张量 → 逐通道只从 4.2e-3 降到 3.85e-3：**FP8 的权重误差是格式本身的（3 位尾数），不是缩放粒度的**
- FP8 全部 Linear 的误差（5.7e-3）大部分来自权重（4.2e-3）
- NVFP4：块缩放隔离了离群值（激活 2.1e-2，与 INT8 同量级），但 1 位尾数让**权重**误差达到 5.5e-2，全部 Linear 8.2e-2

### 结果 ②：任务级（冻结 FP32 门控；`protocol/r7_*`）

| 配置 | held-out R@1 | held-out R@100%P | deployed F1 [95% CI] | FP |
| --- | ---: | ---: | --- | ---: |
| FP32 / FP16 TRT | 0.933 | 0.900 | 0.848 [0.747, 0.926] | 7 |
| 伪量化 FP8 全部 Linear | 0.900 | 0.100 | 0.860 [0.766, 0.938] | 7 |
| **TRT FP8 全部 Linear** | **0.900** | 0.100 | **0.826 [0.719, 0.915]** | 8 |
| 伪量化 NVFP4 全部 Linear | **0.867** | 0.800 | 0.727 [0.600, 0.839] | 10 |

- FP8 达到宽松判据；零误报召回断在**同一个查询 76**（→ 库 72，差 4 帧，分数 0.843 排第 4；`zero_fp_breakpoint.py`）
- **NVFP4 达不到宽松判据**（R@1 0.867 < 0.9）。它的 R@100%P 反而是 0.800——多出的错误分数都很低（排第 25 名以后）。
  又一次说明这个指标由一两个查询决定

### 结果 ③：真实引擎

**FP8**（`export_qdq.py --fmt fp8`，TensorRT 的 FP8 Q/DQ 自定义算子 `TRT_FP8QuantizeLinear` / `TRT_FP8DequantizeLinear`，96 对）：

| 引擎 | 构建 | 大小 | GEMM | MHA |
| --- | ---: | ---: | --- | --- |
| FP8 b1 | 28 s | **22.7 MB** | 48 个全是 FP8 | 12 个 FP16 |
| FP8 b32 | 10 s | 25.8 MB | 48 个 FP8 | FP16 |

- 引擎相对 FP32 的 1−cos 5.7e-3，与模拟（5.7e-3）一致；但引擎与模拟之间逐图的差是 1.7e-3，比 INT8（2.1e-4）大一个数量级——FP8 的舍入在
  TensorRT kernel 与 ModelOpt 模拟之间不完全相同，聚合误差相同

| | TRT FP16 | TRT FP8 | 加速 |
| --- | ---: | ---: | ---: |
| b1 + CUDA Graph（10 轮配对） | 0.520 ms | **0.461 ms** | ×1.13（10/10） |
| b1 **不套** CUDA Graph | 0.914 ms | 1.029 ms | **×0.89（0/10，更慢）** |
| b1 kernel 数 / GPU 工作量 | 90 / 0.517 ms | 114 / 0.483 ms | |
| b32（6 轮配对） | 8.100 ms | 8.339 ms | ×0.97（3/6，分辨不出） |
| b32 GPU 工作量（剖析） | 8.221 ms | 7.061 ms | −14% |
| 进程显存（同一次运行） | 118 MB | **50 MB** | **−58%** |

- **不套 CUDA Graph 时 FP8 比 FP16 更慢**：kernel 从 90 个增加到 114 个（多出的是 FP8 量化/反量化），b1 发射受限，多发射的代价超过了 GPU 省下的时间。
  阶段 3 的"batch 1 由发射次数决定"又一次成立
- ⚠️ **b32 GPU 工作量少了 14%，墙钟却没有变化**。GPU 受限时两者应当同步变化；这里的差距**未归因**（可能是 kernel 之间出现了空档，未验证）
- ⚠️ **显存 50 MB**：加载引擎 32 MB，但**执行上下文只有 4 MB**（FP16 40 MB、INT8 44–50 MB）。为什么 FP8 引擎的执行上下文这么小，**未归因**

**NVFP4：没能建成引擎（工具链限制）**
- 在 CPU 上导出：ModelOpt 的动态块量化要求缩放因子在 GPU 上（`AssertionError: amax must be a CUDA tensor for dynamic block quantization`）
- 在 GPU 上导出（opset 17、23）：**进程没有崩，导出"成功"，但 ONNX 里一个量化节点都没有**——NVFP4 量化器被静默丢掉了，
  用它建出来的会是一个标着 NVFP4 的 FP16 引擎。**没有用这个文件**
- 为此 `export_qdq.py` 加了一道闸门：启用了量化器、导出的 ONNX 里却没有量化节点，就报错退出、不建引擎。
  复现：`python -m deploy.quant.export_qdq --fmt nvfp4 --group linear --tag nvfp4_lin --batch 1 --export-device cuda --build`
  → `❌ 启用了 96 个量化器，但导出的 ONNX 里没有任何量化节点`（Q 0 / DQ 0，MatMul 72），exit 1
- ModelOpt 真正的 FP4 导出路径在它的 ONNX 工具里（`modelopt.torch._deploy` → `modelopt.onnx`），需要 `[onnx]` 附加项——
  阶段 5 安装时因会把 onnx 1.23 降到 1.21、并带进 onnxruntime-gpu 而刻意没装
- 由于 NVFP4 在模拟里已达不到宽松判据，没有为建引擎去改动环境

### 对照预期

| 项 | 预期 | 实测 | |
| --- | --- | --- | --- |
| FP8 全部 Linear | 1e-3 – 5e-3 | 5.7e-3 | ≈ 略高于上沿 |
| FP8 全部（含 LN 输入、卷积） | 与全部 Linear 同量级 | 1.8e-2（3 倍） | ❌ |
| FP8 任务级 | 宽松达到、严格未必 | 宽松达到、严格未达到 | ✅ |

| NVFP4 全部 Linear（仅模拟） | — | — | 0.867 | 0.727 [0.600, 0.839] | 8.2e-2 | 29 |

**支线的最终结论**：
1. **特征级零代价到 FP16 为止**（最大漂移只有余量的 1/3）
2. **任务级在噪声内**的有两个 8 位点：选择性 INT8（精度最好，F1 0.882）与 FP8 全部 Linear（显存最省，50 MB）。
   两者 b1 都比 FP16 快 ~13%，但最大分数漂移都超过余量（2.5 倍、4.5 倍）——50 个查询下没出事，不等于零误报能力被保住
3. 全模型隐式 INT8 与 NVFP4 越过了拐点
4. **batch 1 的延迟瓶颈从头到尾都是 kernel 发射次数**：降精度本身在 b1 最多带来 ~13%；FP8 不套 CUDA Graph 反而更慢

**部署建议**：显存最紧 → FP8 全部 Linear；在低精度里要精度最好 → 选择性 INT8；对误报零容忍 → FP16。任何一种都要套 CUDA Graph。
